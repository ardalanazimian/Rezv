#  baselineِ اختلافِ ایندکس بینِ دو مسیرِ اسکیما
#
#  هر خط یک ایندکس است که مسیرِ `prisma db push` (CI) می‌سازد ولی مسیرِ
#  `migrate deploy + apply-sql.sh` (تولید) نمی‌سازد، **و بررسی شده که بی‌ضرر
#  است**. tools/check-schema-drift.sh فقط روی خطی که اینجا نیست می‌شکند.
#
#  ⚠️ این فایل بدهیِ ثبت‌شده است، نه وضعِ مطلوب. کوچک‌شدنش پیشرفت است.
#  ⚠️ چیزی را اینجا اضافه نکن مگر ثابت کرده باشی تولید معادلِ کارآمدی دارد.
#
#  تاریخِ ساخت: ۲۰۲۶-۰۸-۲۵ — بعد از مهاجرتِ ۰۶۶ که ۲۰ ایندکسِ واقعاً غایب را
#  ساخت. قبل از ۰۶۶ این فهرست ۲۱ خط بود؛ حالا ۱ خط.
#  فرمت: [UNIQUE ] public.<table> USING <method> (<cols>)[ WHERE (<pred>)]
# ═══════════════════════════════════════════════════════════════════════════

# jobs.idempotency_key — تولید معادلِ **کاملاً کارآمدترِ** آن را دارد:
#   CI   : UNIQUE ... (idempotency_key)                              [Prisma @unique]
#   تولید: UNIQUE ... (idempotency_key) WHERE (idempotency_key IS NOT NULL)  [idx_jobs_idem]
# چون btree در Postgres NULLها را به‌هرحال یکتا نمی‌شمارد، این دو برای
# dedupِ صف (api/src/lib/queue.ts:63 که روی خطای P2002 تکیه می‌کند) رفتارِ
# یکسان دارند. تأییدِ اجرایی (۲۰۲۶-۰۸-۲۵، دو Postgresِ واقعی): دو INSERT با
# همان idempotency_key روی هر دو DB → هر دو خطای unique دادند و ۱ ردیف ماند.
UNIQUE public.jobs USING btree (idempotency_key)
