# ADR 0002 — وب‌سایتِ عمومی، CMS و قیفِ فروش

**وضعیت:** پذیرفته‌شده · **تاریخ:** ۱۴۰۵-۰۵ · **مرتبط با:** ADR 0001 (معماریِ رندرِ SEO)

---

## زمینه

رزرونو سه اپِ محصولی داشت (مشتری، کسب‌وکار، شرکت) و یک لایه‌ی SEO (`apps/seo`)
که فقط صفحاتِ رستوران/شهر/آشپزی را سرو می‌کرد. آنچه نبود:

- جایی که خودِ محصول معرفی شود و بازدیدکننده را به مشتری تبدیل کند
- مسیرِ واقعیِ «دموی رایگان» و «خریدِ اشتراک»
- ابزاری برای ویرایشِ متن/قیمت/سئو بدونِ انتشارِ نسخه‌ی جدید

## تصمیم

### ۱) وب‌سایت یک اپِ مستقل است: `apps/landing`

> **بازنگری.** نسخه‌ی اولِ این ADR وب‌سایت را داخلِ `apps/seo` گذاشته بود تا یک
> دامنه و یک sitemap داشته باشیم. مالکِ محصول جداییِ کامل را خواست: وب‌سایت
> باید محصولی مستقل با دامنه، سئو و داشبوردِ خودش باشد و اپ‌های موجود
> (`seo`, `business`, `customer`, `company`) دست‌نخورده بمانند. تصمیمِ زیر
> جایگزینِ آن شد و `apps/seo` دقیقاً به حالتِ پیش از این کار برگردانده شد.

| اپ | مسئولیت | دامنه |
|---|---|---|
| `apps/landing` | معرفیِ محصول، فروشِ اشتراک، داشبوردِ محتوا | دامنه‌ی خودش |
| `apps/seo` | صفحاتِ ایندکس‌پذیرِ رستوران/شهر/آشپزی (ADR 0001) | دامنه‌ی خودش |

**هزینه‌ای که آگاهانه پذیرفته شد:** دو `sitemap.xml`، دو canonical root، و
لینک‌سازیِ داخلیِ بینِ محتوا و صفحاتِ رستوران که حالا cross-domain است. برای
اینکه این هزینه به خطا تبدیل نشود:

- `NEXT_PUBLIC_SITE_URL` هر اپ باید دامنه‌ی خودش باشد. در `apps/landing`
  دامنه از env می‌آید و hardcode نیست (`lib/i18n.ts`) — وگرنه دو اپ روی یک
  آدرس ادعای مالکیت می‌کردند.
- sitemap اپِ لندینگ **هیچ آدرسِ رستورانی ندارد**. اعلامِ آدرسی که آن اپ سرو
  نمی‌کند یعنی ۴۰۴ در sitemap؛ این با تست بررسی می‌شود.

هر کدام یک پروژه‌ی Vercelِ مستقل‌اند (`Root Directory` = `apps/landing` و
`apps/seo`). پورتِ توسعه: لندینگ ۳۲۰۰، سئو ۳۱۰۰ — تا همزمان بالا بیایند.

### ۱-الف) صفحه‌سازی از داشبورد، بدونِ دیپلوی

مسیرِ `app/[slug]/page.tsx` هر اسلاگی را که در استودیو ساخته شده رندر می‌کند،
با `dynamicParams` روشن تا اسلاگی که موقعِ build نبوده هم کار کند.

پیش از این، `sitemap.ts` آدرسِ صفحه‌های ساخته‌شده در استودیو را اعلام می‌کرد
ولی هیچ مسیری رندرشان نمی‌کرد — یعنی **۴۰۴ در sitemap**. مسیرهای ثابت در Next
بر مسیرِ پویا اولویت دارند، پس `/pricing` همچنان صفحه‌ی واقعیِ خودش را می‌گیرد؛
یک فهرستِ `RESERVED` هم لایه‌ی دومِ دفاع است تا رکوردِ CMS با اسلاگِ یک مسیرِ
واقعی، بی‌صدا جای آن را نگیرد.

### ۲) محتوا در دیتابیس، نه در کد

جدول‌های `site_pages`, `site_articles`, `site_faqs`, `site_plans`,
`site_testimonials`, `site_banners`, `site_release_notes` (migration 031).

هر صفحه یک آرایه از **بلوک‌ها** است (`hero`, `features`, `pricing`, `faq`, …).
سایت بلوکِ ناشناخته را بی‌صدا رد می‌کند، پس افزودنِ بلوکِ تازه از استودیو هرگز
صفحه‌ی زنده را نمی‌شکند.

**حالتِ امن:** `shared/content/site-content.json` منبعِ واحدِ محتوای پیش‌فرض است و
با `tools/sync-design-system.sh` به دو مصرف‌کننده کپی می‌شود:
`apps/landing/content/` (رندر وقتی API در دسترس نیست) و `api/prisma/seed/`
(نصبِ تازه). یک متن، دو مصرف‌کننده، و CI با `--check` واگرایی را می‌گیرد.

### ۳) قیفِ فروش یک جدول است، نه دو سیستم

`site_orders` هم دموی رایگان (`kind=trial`) و هم درخواستِ خرید
(`kind=purchase`) را نگه می‌دارد؛ `site_inquiries` تماس با فروش را.

- **دمو** بلافاصله provision می‌شود: `Tenant` + `Restaurant` (+ چیدمانِ اولیه‌ی
  میز) + `Staff(owner)` واقعی، با `trialEndsAt = now + 30d`. کاربر همان لحظه
  می‌تواند با شماره‌اش وارد پنلِ کسب‌وکار شود. **idempotent روی شماره.**
- **خرید** با وضعیتِ `pending` ثبت می‌شود. قیمت هرگز از کلاینت گرفته نمی‌شود:
  فقط `plan_key` می‌آید و سرور مبلغ را از `site_plans` می‌خواند و روی سفارش
  **اسنپ‌شات** می‌کند (تغییرِ بعدیِ قیمت، سندِ سفارشِ قدیمی را عوض نمی‌کند).
- **فعال‌سازی** فقط از پنلِ شرکت/استودیو: `tenant.plan` و `planExpiresAt`
  واقعاً ست می‌شوند (با قفلِ خوش‌بینانه روی `tenant.version`)، و «چه‌کسی، چه
  زمانی، با چه یادداشتی» روی همان ردیف + `audit_logs` ثبت می‌شود.

بدونِ FK از `site_orders` به `site_plans`: پلن ممکن است حذف/بازنویسی شود ولی
تاریخچه‌ی مالیِ سفارش باید تغییرناپذیر بماند.

### ۴) استودیو هویتِ جدا نمی‌سازد

`/studio` با همان OTPِ مدیرِ پلتفرم (`/auth/admin/*`) کار می‌کند و همه‌ی
نوشتن‌هایش از `/api/v1/admin/site/*` عبور می‌کند. یعنی یک صفِ دسترسی، یک
جای audit. پنلِ شرکت هم همان صف را در بخشِ «درخواست‌های سایت» می‌بیند.

### ۵) دو لایه‌ی کش، دو مکانیزمِ باطل‌سازی

| لایه | باطل‌سازی |
|---|---|
| Redisِ بک‌اند (`site-content:*`) | خودکار در هر نوشتنِ استودیو |
| ISRِ Next (HTMLِ صفحه) | `POST /api/revalidate` که استودیو بعد از ذخیره صدا می‌زند |

`/api/revalidate` کلیدِ مشترک ندارد (در مرورگر امن نیست): توکنِ مدیر را به خودِ
API می‌فرستد و اگر یک endpointِ مدیریتی پذیرفتش، تماس‌گیرنده واقعاً مدیر است.

### ۶) ریشه‌ی دامنه به وب‌سایت می‌رسد؛ بقیه به زیردامنه

تصمیمِ ۱ (وب‌سایت مالکِ ریشه است) با `Caddyfile`ِ آن‌زمان در تضاد بود: آنجا اپِ
مشتری روی `/` نشسته بود و پنل‌ها روی `/business` و `/company`. اگر هر دو را روی
`rezervno.ir` می‌گذاشتیم، به هم می‌خوردند.

| دامنه | چه چیزی | کجا میزبانی می‌شود |
|---|---|---|
| `rezervno.ir` | وب‌سایتِ عمومی (`apps/landing`) | Vercel |
| `find.rezervno.ir` | صفحاتِ رستوران (`apps/seo`) — دامنه‌اش انتخابِ توست | Vercel |
| `api.rezervno.ir` | بک‌اند | این سرور |
| `app.rezervno.ir` | اپِ مشتری | این سرور |
| `business.rezervno.ir` | پنلِ کسب‌وکار | این سرور |
| `admin.rezervno.ir` | پنلِ شرکت | این سرور |

⚠️ دو اپِ Vercel نباید روی یک دامنه بنشینند. هرکدام `NEXT_PUBLIC_SITE_URL`
خودش را دارد؛ اگر هر دو یک مقدار بگیرند، canonicalهای متناقض تولید می‌شود.

**هر زیردامنه `/api/*` خودش را به `api:3000` پروکسی می‌کند.** پنل‌ها API را
same-origin صدا می‌زنند (`resolveApiBase()` پیش‌فرض `''` برمی‌گرداند)، پس با این
کار نه متاتگِ `rz-api-base` لازم می‌شود، نه preflightِ CORS، نه بازکردنِ
`connect-src` در CSP — یعنی پنل‌ها بدونِ حتی یک خط تغییر منتقل می‌شوند.

این جایگزینِ `ALLOWED_ORIGINS` **نیست**: مرورگر روی درخواستِ mutating حتی
same-origin هم `Origin` می‌فرستد و `middleware.ts` هر مبدأِ خارج از فهرست را
۴۰۳ می‌کند. پس هر چهار زیردامنه باید در `ALLOWED_ORIGINS` باشند.

هنگامِ این تغییر دو باگِ قدیمی در `Caddyfile` هم پیدا و رفع شد (با
`caddy adapt` روی خروجیِ JSON دیده شدند):

- `respond @sensitive 404` و `respond @badbots 403` **هرگز اجرا نمی‌شدند**.
  Caddy دستورها را بازچینش می‌کند و `handle` را جلوتر از `respond` می‌گذارد؛
  چون سایت یک `handle`ِ فراگیر داشت، همه‌ی درخواست‌ها همان‌جا پاسخ می‌گرفتند.
  حالا خودشان `handle` هستند و اولِ گروه قرار می‌گیرند.
- مچرِ `header User-Agent *sqlmap* *nikto* …` به‌صورتِ جفت‌های `<field> <value>`
  پارس می‌شد، یعنی عملاً فقط `sqlmap` چک می‌شد و بقیه به نامِ هدرِ بی‌معنا
  تبدیل می‌شدند. با `header_regexp` جایگزین شد.

## پیامدها

**مثبت**

- وب‌سایت محصولی مستقل است: دیپلوی، دامنه، سئو و چرخه‌ی انتشارِ خودش را دارد و
  تغییرش هیچ‌کدام از چهار اپِ دیگر را لمس نمی‌کند
- قیمت/متن/سئو بدونِ ری‌دیپلوی قابلِ ویرایش‌اند
- صفحه‌ی تازه از داشبورد ساخته می‌شود و بدونِ دیپلوی زنده است
- دموی رایگان یک ردیفِ واقعی در دیتابیسِ محصول است، نه فرمِ سرنخ
- مسیرِ خرید برای مشتری شفاف است (`/order/{code}`) و برای تیم قابلِ ردیابی

**منفی / بدهی**

- دو دامنه یعنی دو `sitemap.xml` و دو canonical root. لینکِ بینِ صفحاتِ
  بازاریابی و صفحاتِ رستوران cross-domain است و اعتبارِ لینک را مثلِ لینکِ
  داخلی منتقل نمی‌کند. این هزینه‌ی آگاهانه‌ی جداییِ کامل است.
- نظرهای مشتریان عمداً seed نمی‌شوند: نقلِ‌قولِ ساختگی نمی‌سازیم. تا انتشارِ
  نظرِ واقعی از استودیو، آن بخش «حالتِ خالی» نشان می‌دهد.
- پرداختِ آنلاینِ خودکار پیاده نشده؛ فعال‌سازی عمداً دستی و انسانی است.

## پیکربندی

| متغیر | محل | کاربرد |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | apps/landing | دامنه‌ی همین سایت — پایه‌ی canonical و sitemap |
| `SITE_API_BASE` | apps/landing (سرور) | خواندنِ محتوا در SSR/ISR و sitemap |
| `NEXT_PUBLIC_API_BASE` | apps/landing (مرورگر) | فرم‌های دمو/خرید/تماس و استودیو |
| `NEXT_PUBLIC_BUSINESS_APP_URL` | apps/landing | لینکِ ورود به پنلِ کسب‌وکار |
| `NEXT_PUBLIC_CUSTOMER_APP_URL` | apps/landing | لینکِ ورود به اپِ مشتری |
| `NEXT_PUBLIC_COMPANY_APP_URL` | apps/landing | لینکِ ورود به پنلِ شرکت |
| `ALLOWED_ORIGINS` | api | **باید دامنه‌ی سایت را شامل شود** وگرنه فرم‌ها CORS می‌خورند |
| `SALES_NOTIFY_EMAIL` | api (یا تنظیمِ `sales_notify_email`) | گیرنده‌ی اعلانِ سفارش/پیام |
| `PLATFORM_ADMIN_TENANT_ID` | api | بدونِ آن، استودیو و پنلِ شرکت باز نمی‌شوند |

## راه‌اندازی

```sh
# ۱) اسکیما و محتوای پیش‌فرض
cd api
npm run db:migrate           # یا: npx prisma migrate deploy
sh prisma/apply-sql.sh       # شاملِ 031-site-cms-and-funnel.sql
npm run db:seed:site         # پلن‌ها، صفحه‌ها، پرسش‌ها، مقاله‌ها

# ۲) وب‌سایت (پورت ۳۲۰۰)
cd ../apps/landing
npm install
SITE_API_BASE=https://api.rezervno.ir NEXT_PUBLIC_API_BASE=https://api.rezervno.ir npm run dev
```

بازگرداندنِ عمدیِ محتوا به نسخه‌ی پیش‌فرض: `npm run db:seed:site -- --force`
(به‌صورتِ پیش‌فرض ردیف‌های موجود دست‌نخورده می‌مانند تا ویرایش‌های استودیو
بازنویسی نشوند).

## نکته‌ی جانبیِ مهم

هنگامِ پیاده‌سازی مشخص شد `middleware.ts` در ریشه‌ی `api/` قرار داشت در حالی که
App Router زیرِ `api/src/app/` است. Next.js آن را **اصلاً اجرا نمی‌کرد** — یعنی
CORS، چکِ Origin (ضدِ CSRF)، ریت‌لیمیتِ سراسری و هدرهای امنیتی (CSP/HSTS) روی
هیچ پاسخی اعمال نمی‌شدند. فایل به `api/src/middleware.ts` منتقل شد و با تستِ
مستقیمِ هدرها تأیید شد که حالا اجرا می‌شود.
