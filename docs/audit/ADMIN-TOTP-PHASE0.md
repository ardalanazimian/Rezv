# ورودِ مدیر با TOTP — گزارشِ فازِ ۰ (کاوش)

> ۲۰۲۶-۰۸-۲۹ · شاخه: `main` (`c0327c2`) · **هیچ کدی نوشته نشده**
> دامنه: فقط پنلِ **company**. پنل‌های business و customer روی OTP می‌مانند.
> TOTP = RFC 6238 (Google Authenticator / Aegis) — کاملاً آفلاین، **بدونِ** OAuth
> و بدونِ هیچ ارتباطی با `accounts.google.com`.

---

## خلاصه‌ی اجرایی

کاوش یک چیزِ تعیین‌کننده نشان داد: **ورود با نامِ کاربری و رمز برای پنلِ
company از قبل وجود دارد و کار می‌کند.** پس این کار «ساختنِ مسیرِ ورودِ تازه»
نیست، «افزودنِ عاملِ سوم به مسیرِ موجود» است. مسیرِ دومِ موازی ساخته نمی‌شود.

خبرِ دوم: `principal`ی که آن مسیر صادر می‌کند **همین حالا** دقیقاً همان
`platform-admin`ِ معمول است — پس شرطِ ⭐ شما (RBAC و tenant isolation
دست‌نخورده) بدونِ هیچ تغییری برقرار است.

## ۱. `BREAK_GLASS_*` — چه می‌کند و چرا کافی نیست

**مسیر:** [`api/src/lib/otp.ts:69-101`](../../api/src/lib/otp.ts#L69-L101) — تابعِ
`breakGlassCodeFor(normalizedPhone)`.

**رفتار:** اگر `BREAK_GLASS_PHONE` و `BREAK_GLASS_CODE` هر دو ست باشند و شماره‌ی
درخواست دقیقاً همان شماره باشد، به‌جای کدِ تصادفی همان **کدِ ثابت** استفاده
می‌شود. سه گارد دارد:

| گارد | خط | کار |
|---|---|---|
| ۱ | `otp.ts:83` | هر دو متغیر لازم است — کامنتِ خودِ فایل صادقانه می‌گوید این خط **افزونه** است (جهش‌آزمایی: ۰ از ۱۲ تست قرمز شد) |
| ۲ | `otp.ts:85` | کد باید دقیقاً ۶ رقم باشد، وگرنه قابلیت **غیرفعال** می‌ماند (نه نیمه‌فعال) |
| ۳ | `otp.ts:95` | فقط همان یک شماره |

نقطه‌ی فراخوانی: [`otp.ts:113`](../../api/src/lib/otp.ts#L113) داخلِ `requestOtp` —
عمداً **بعد** از `enforceRateLimit` تا این مسیر هم محدود بماند.

### حکم: پوششش نمی‌دهد

سه دلیل:

1. **همچنان روی زنجیره‌ی SMS سوار است.** خروجی‌اش یک ردیفِ `otpCode` است که
   باید از مسیرِ `verify` رد شود. اگر ترانسپورتِ پیامک قفل باشد (وضعیتِ
   امروز) این مسیر مشکلِ ما را حل می‌کند، ولی وابسته به همان زنجیره می‌ماند.
2. **کد ثابت است، نه چرخشی.** یک رازِ بلندمدت در env در برابرِ کدی که هر ۳۰
   ثانیه عوض می‌شود.
3. **کامنتِ خودِ کد** (`otp.ts:63`) می‌گوید «باید پیش از لانچِ عمومی برداشته
   شود و متریکش باید صفر بماند».

> پس رویش نمی‌سازیم و دستش هم نمی‌زنیم. TOTP روی **مسیرِ رمز** می‌نشیند که
> جای درستِ معماری‌اش است. break-glass طبقِ برنامه‌ی خودش پیش از لانچ برداشته
> می‌شود.

## ۲. ⭐ مسیرِ فعلیِ ورودِ پنلِ company

سه مسیرِ ورودِ ادمین وجود دارد:

| مسیر | فایل | عامل |
|---|---|---|
| **رمز** | [`api/src/app/api/v1/auth/admin/login/route.ts`](../../api/src/app/api/v1/auth/admin/login/route.ts) (۶۴ خط) | username + password |
| OTP — درخواست | `api/src/app/api/v1/auth/admin/request/route.ts` | پیامک |
| OTP — تأیید | `api/src/app/api/v1/auth/admin/verify/route.ts` | پیامک |

### آنچه مسیرِ رمز امروز انجام می‌دهد

```
POST /api/v1/auth/admin/login   { username, password }
```

- خط ۳۱ — fail-closed رویِ `PLATFORM_ADMIN_TENANT_ID`
- خط ۳۵ — `authenticateStaffByPassword` (فقط احرازِ هویت)
- خط ۴۰ — **مجوز جدا از احراز**: `tenantId === platformTenantId` و
  `role === 'owner'` و `isActive` — یعنی کارمندِ عادی با رمزِ درستِ خودش هم رد
  می‌شود
- خط ۴۶ و ۵۶ — `audit` برای **هر دو** حالتِ موفق و ناموفق، با IP

### 🔑 principal که صادر می‌کند

[`login/route.ts:44`](../../api/src/app/api/v1/auth/admin/login/route.ts#L44):

```ts
const principal = { sub: staff.id, kind: 'staff' as const,
                    tenantId: staff.tenantId, role: 'owner' as const };
```

**این دقیقاً همان چیزی است که در بندِ ⭐ خواستید.** هیچ نوعِ تازه‌ای لازم
نیست؛ افزودنِ TOTP به این مسیر، شکلِ توکن را اصلاً لمس نمی‌کند.

## ۳. `adminAuthFromRequest` و ساختِ principal

`adminAuthFromRequest` **وجود ندارد** — نامِ مرده است، همان‌طور که `CLAUDE.md`
هم ثبت کرده. جایگزینِ زنده:

[`api/src/lib/admin-auth.ts:39`](../../api/src/lib/admin-auth.ts#L39) —
`requireAdmin(req)`.

| مرحله | خط | کار |
|---|---|---|
| توکن | ۴۲ | `verifyAccess` |
| شکلِ principal | ۴۳ | `kind === 'staff'` **و** `role === 'owner'` |
| پیکربندی | ۴۸ | **fail-closed** — بدونِ `PLATFORM_ADMIN_TENANT_ID` هیچ دسترسی |
| تنانت | ۵۱ | `tenantId === PLATFORM_ADMIN_TENANT_ID` |
| **حقیقت از DB** | ۵۹ | نقش و `isActive` **دوباره از دیتابیس** خوانده می‌شود، نه از توکن |

خطِ ۵۹ برای تصمیمِ (ج) پایین حیاتی است: هر توکنی که `sub`ش در جدولِ `staff`
نباشد، در اولین درخواستِ ادمین رد می‌شود.

## ۴. کتابخانه‌ی TOTP — باید اضافه شود

```
otpauth    نیست
otplib     نیست
speakeasy  نیست
notp       نیست
qrcode     ✅ موجود
```

`qrcode` موجود بودن یعنی اسکریپتِ فازِ ۲ **بدونِ وابستگیِ تازه** می‌تواند QR را
در ترمینال بکشد.

**دو گزینه برای خودِ TOTP:**

| گزینه | سود | هزینه |
|---|---|---|
| `otpauth` | جاافتاده، TypeScriptِ خالص، بدونِ وابستگیِ بومی | یک وابستگیِ تازه |
| پیاده‌سازیِ RFC 6238 رویِ `crypto.createHmac('sha1')` | صفر وابستگی؛ الگوریتم ثابت و ~۲۵ خط | کدِ رمزنگاریِ خانگی، هرچند بسیار کوچک و کاملاً استاندارد |

## ۵. هشِ رمز — نه Argon2، نه bcrypt، بلکه **scrypt**

```
argon2  · @node-rs/argon2 · bcrypt · bcryptjs   → هیچ‌کدام نصب نیست
```

ولی پروژه از قبل هش دارد:
[`api/src/lib/password.ts:61-67`](../../api/src/lib/password.ts#L61-L67)

```ts
const hash = await scrypt(plain, salt, KEYLEN, { N, r: R, p: P, maxmem: MAXMEM });
return `scrypt$${N}$${R}$${P}$${salt.toString('base64')}$${hash.toString('base64')}`;
```

پارامترها (`password.ts:34-39`): `N=32768`، `r=8`، `p=1`، `keylen=64`،
`salt=16B`، `maxmem=64MB`.

مقایسه در [`password.ts:93`](../../api/src/lib/password.ts#L93) با
`timingSafeEqual` — یعنی **constant-time از قبل برقرار است**. و
[`password.ts:77`](../../api/src/lib/password.ts#L77) عمداً هرگز throw نمی‌کند
تا تفاوتِ ۵۰۰/۴۰۱ به مهاجم چیزی نگوید.

> **پیشنهاد: همین scrypt.** حافظه‌سخت، از bcrypt قوی‌تر، بدونِ وابستگیِ بومی
> (Argon2 نیازِ کامپایل دارد)، و از قبل در همین مخزن تست‌شده است. شما نوشتید
> «Argon2id، یا bcrypt اگر نبود» — scrypt از گزینه‌ی دومِ شما بهتر است.

## سه تصمیمی که پیش از فازِ ۱ لازم است

### الف) کتابخانه‌ی TOTP
`otpauth` (یک وابستگیِ تازه) یا پیاده‌سازیِ ~۲۵ خطی رویِ `crypto` (صفر وابستگی)؟

### ب) هشِ رمز
`scrypt`ِ موجود (پیشنهادِ من) یا اصرار بر Argon2id؟

### ج) ⚠️ مهم‌ترین — منبعِ هویت

شما نوشتید `ADMIN_USERNAME` و `ADMIN_PASSWORD_HASH` از **env** بیایند. ولی
مسیرِ فعلی کاربر را از **دیتابیس** می‌خواند. این دو با هم جمع نمی‌شوند:

| گزینه | چه می‌شود | اثر رویِ ⭐ |
|---|---|---|
| **۱ — TOTP رویِ مسیرِ موجود** | اعتبارنامه از DB می‌ماند؛ فقط `ADMIN_TOTP_SECRET` از env | ✅ RBAC و `requireAdmin` کاملاً دست‌نخورده |
| **۲ — هر سه از env** | هویتی که در جدولِ `staff` نیست | ❌ `requireAdmin` در [خطِ ۵۹](../../api/src/lib/admin-auth.ts#L59) نقش را از DB می‌خواند و آن توکن را **رد می‌کند** — مگر آن گارد دست بخورد، که دقیقاً نقضِ ⭐ است |

**توصیه: گزینه‌ی ۱.**

ولی اگر منظورتان این است که «حتی وقتی DB خالی یا خراب است هم باید بتوانم وارد
شوم» — آن‌وقت گزینه‌ی ۲ لازم است و باید تکلیفِ `requireAdmin` را صریح روشن
کنیم (مثلاً یک شاخه‌ی env-only که فقط وقتی `ADMIN_LOGIN_ENABLED` روشن است
فعال می‌شود و در audit با کانالِ متمایز ثبت می‌گردد).
