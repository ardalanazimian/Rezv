### S-09 — whether S-02/S-03 are actually closed depends on one unmeasured fact: the production DB role

**Opened 2026-09-18 by Red Team `rezv-18` from a live attack on an isolated DB (`rt18_attack`, real 089+090 triggers). This is the hinge of the entire money-integrity story.**

What HOLDS, proven live rather than read: `points_ledger` resists `UPDATE`, `DELETE` and `TRUNCATE` **even as table owner and superuser** — balance stayed at 100. A balance cannot be moved without appending a row through normal DML. The `audit_logs` conditional retention guard also holds: a recent delete is blocked, a >1-year retention delete is allowed, and aging a recent row via `UPDATE` to sneak it past the window is blocked — so recent evidence can be neither deleted nor backdated.

**Two escapes exist, and both require elevated database privilege:**

| Escape | Privilege needed | Caught by the census? |
|---|---|---|
| `session_replication_role = 'replica'` | SUPERUSER | **No** — runtime and session-local. The FP-009 §6 static guard scans `api/src` for the token and cannot stop a runtime `SET` by a privileged process |
| `ALTER TABLE … DISABLE TRIGGER` | table OWNER | **Yes** — proved live, `UPD_ACTIVE` 1 → 0 → 1 |

**So everything turns on one question nobody has measured: what privilege does the production connection role hold?**
- If it is a **plain role** — not superuser, not the owner of these tables — neither escape is reachable by a compromised API, and 089/090 close the money-integrity story completely.
- If the **unrefuted P0-022 claim** is true and production runs owner + superuser + `BYPASSRLS`, then **a compromised application can move the money ledger**, and every trigger shipped this week is decoration on that path.

Same code, opposite verdict, decided entirely by configuration. Status **UNKNOWN**: there is no `api/.env` on this machine and no deployed environment, so it has only ever been measured against CI — whose role is superuser and owner by construction, which is a property of the harness and evidence of nothing about production. Red Team explicitly declined to infer from it.

**Decided: P0-022 becomes a named gate item**, assigned to Red Team ahead of payment-callback replay and double-spend. The gate must read `current_user`, `pg_roles` and `pg_class.relowner` **from the live connection, never from a config file** — a config file is a claim, the connection is the fact — assert not-superuser, not-owner, no `BYPASSRLS`, be falsifiable **per axis** (granting superuser to a scratch role must turn it red; proving the superuser axis says nothing about the ownership axis), and **report UNKNOWN and fail closed** where no production exists rather than passing silently.
