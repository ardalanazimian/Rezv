# پروفایلِ مشتری — ممیزیِ میدان‌به‌میدان (پروتکل §۱۳ و §۱۴)

> اصلِ راهنما از خودِ پروتکل: **«وجودِ یک ستون در دیتابیس یعنی وجودِ قابلیت
> نیست.»** هر ردیف تا انتهایِ زنجیره دنبال شده:
> DB → API → مجوز → اعتبارسنجی → فرانت → پایداری → بازیابی → تست.
>
> تاریخِ ممیزی: ۲۰۲۶-۰۸-۲۴ · روش: grep رویِ کلِ `api/src` و هر سه فرانت،
> به‌علاوه‌ی فراخوانِ زنده رویِ سرورِ واقعی با Postgres و Redisِ واقعی.

## ۲. آنچه در این پاس رفع شد — رضایتِ ارتباطی

### مسئله‌ی واقعی

اپِ مشتری از قبل پنج کلیدِ ترجیحِ اعلان داشت. ولی:

```
setNotifPref(id, on) → localStorage.setItem(...)   ← و تمام
```

و سمتِ سرور: `grep -rn "notif_pref|consent|optOut|marketingOptIn" api/src` →
**صفر نتیجه**. یعنی هیچ ستونی، هیچ فیلدی، هیچ چکی وجود نداشت.

نتیجه‌ی عملی: کاربری که «تخفیف و کش‌بک ویژه» را خاموش می‌کرد **همچنان پیامکِ
کمپینِ تبلیغاتی می‌گرفت** — چون `POST /restaurant/sms` همه‌ی اعضایِ باشگاه را
بدونِ هیچ فیلترِ رضایتی صدا می‌زد. و انتخابش با پاک‌کردنِ حافظه‌ی مرورگر برایِ
همیشه از بین می‌رفت. این هم §۱۳ است، هم §۱۷ (consent)، هم §۳ (کنترلی که
نتیجه‌ی واقعی ندارد).

### رفع

| لایه | تغییر |
|---|---|
| DB | migration `050-notification-consent.sql` — ستونِ `users.notification_prefs jsonb NOT NULL DEFAULT '{}'` |
| Prisma | `User.notificationPrefs Json @default("{}")` (گاردِ schema-drift سبز) |
| منطق | `lib/notification-prefs.ts` — دسته‌ها، `readNotificationPrefs`، `allowsCategory` |
| API | `GET/PATCH /me/notification-prefs` — merge، نه جایگزینی |
| اجرا | `POST /restaurant/sms` حالا منصرف‌شده‌ها را حذف می‌کند و `opted_out` را برمی‌گرداند |
| کلاینت | `setNotifPref` واقعاً PATCH می‌زند؛ شیت با حقیقتِ سرور بازنقاشی می‌شود |

### تصمیمِ طراحیِ کلیدی: «فقط انصرافِ صریح»

کلیدِ **غایب** یعنی «کاربر نظری نداده»، نه «انصراف داده». اگر غیبت را انصراف
فرض می‌کردیم، همه‌ی کاربرانِ موجود بی‌صدا از **یادآوریِ رزروشان** محروم
می‌شدند — رگرسیونی بدتر از خودِ باگ. تستِ اختصاصی این قاعده را قفل می‌کند.

همچنین `reminder` عمداً در `MARKETING_CATEGORIES` **نیست**: یادآوریِ رزرو
تراکنشی است و نباید با انصراف از تبلیغات خاموش شود.

### راستی‌آزمایی (نه فرض)

- ۷ تستِ واحد: `api/tests/notification-consent.test.mts`
- ۲ تستِ E2E روی سه پروفایلِ CI
- فراخوانِ زنده رویِ سرورِ واقعی + Postgresِ واقعی:
  `{"prefs":{}}` → PATCH `{"offers":false}` → `{"prefs":{"offers":false}}` →
  GET دوباره پایدار ماند. کلیدِ ناشناخته (`evil`) در ستون ننشست.
- هر دو تستِ E2E با تزریقِ عمدیِ همان باگ قرمز شدند و بعد بازگردانده شدند.

## ۳. آنچه رفع **نشد** — و چرا

| مورد | چرا نه |
|---|---|
| `GuestProfile.dietaryTags` (ستونِ یتیم) | ستون در جدولِ **تجمیعیِ** `guest_profiles` است که با `rebuildGlobalProfiles()` از رزروها بازسازی می‌شود — و آن SQL این ستون را پر نمی‌کند. پرکردنش یک تصمیمِ محصولی است: آیا آلرژیِ سطحِ پروفایل باید از رزروها **استنتاج** شود (دادهٔ OBSERVED طبقِ §۱۷) یا کاربر صریح واردش کند (EXPLICIT)؟ پروتکل §۱۷ صریحاً می‌گوید این دو را قاطی نکنید. تا وقتی محصول تصمیم نگیرد، پرکردنِ خودکار **بدتر** از خالی‌بودن است. |
| ترجیحِ نشستن · ترجیحاتِ حریمِ خصوصی · دسترسی‌پذیریِ سمتِ مشتری | هیچ ستون، API یا UI ندارند. ساختنشان یعنی **ویژگیِ تازه**، نه بازیابی — و §۳۵ صریح است: «صرفاً به این دلیل که در نقشه‌راه است نساز.» به‌عنوان شکافِ ثبت‌شده می‌مانند. |
| فرمِ واردکردنِ تاریخِ تولد | بک‌اند از قبل `birth_date` را می‌پذیرد و پاداشِ تولد/کمپینِ تولد به آن وابسته‌اند، ولی هیچ فرمی در اپ آن را نمی‌فرستد. کارِ کوچکی است ولی **UI جدید** است، نه رفعِ باگ. |

## ۴. §۱۴ — ایمنیِ غذایی: از قبل کار می‌کرد

برخلافِ سطحِ پروفایل، مسیرِ **هر رزرو** کامل و تأییدشده است:

```
شیتِ رزروِ مشتری → POST /reservations {preferences}
  → Reservation.preferences (String[])
  → GET /restaurant/reservations  (note = r.preferences.join)
  → کارکنانِ مجاز
```

با تستِ E2Eِ اختصاصی (`allergy-safety-flow.spec.ts`). مرزِ حریمِ خصوصی هم
درست است: رستوران فقط اطلاعاتِ لازم برایِ سرویسِ ایمن را می‌بیند، نه کلِ
پروفایلِ مشتری.

**تقویتِ این پاس:** کلیدهایِ `preferences`, `dietary*`, `allergies`, `phone`,
`email`, `birth_date` به فهرستِ redactionِ لاگ اضافه شدند
(`lib/logger.ts`) — پروتکل §۳۴ صریحاً می‌گوید اطلاعاتِ آلرژی نباید لاگ شود.
هیچ لاگی امروز این‌ها را پاس نمی‌داد (تأییدشده با grep)، پس این دفاعِ
پیشگیرانه است نه رفعِ نشت.
