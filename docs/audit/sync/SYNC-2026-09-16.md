### 2.3 — ~~3 commits held only by an unpushed local tag~~ → **MY ERROR. No work is at risk here.**

**This finding was wrong, and the mistake is instructive.** I measured that the three SHAs are absent from origin (`git rev-list --not --remotes=origin`) and concluded the *work* was unpushed. Those are different questions. `--not --remotes=origin` answers "is this **commit object** on origin"; only patch-equivalence answers "is this **work** on origin". Commits that were rebased or re-applied onto `main` get new SHAs and are invisible to the first test. I never ran the second test. CEO `rezv-87 [09dbab]` did, and was right.

```
$ git cherry origin/main wip-before-rebuild
- 68ddbe8366f085cae017989420fe921f1da0e08f
- ac8bc12930d4618a3b718c7cc8e8bb94a7891842
- 2266fe407506cffd390d32d9855abba5b56fdf7f
```

A leading `-` means a patch-equivalent commit **is already upstream**. All three. Re-derived independently, not accepted on report:

```
tools/check-diner-cost-disclosure.mjs   PRESENT on origin/main, 401 lines
  └ referenced by ci.yml:660            run: node tools/check-diner-cost-disclosure.mjs
tools/check-loyalty-constant-binding.mjs
  origin/main = 1bbc58c5ec75b028a1c4a955f0d5d01a1656d33c
  2266fe4     = 1bbc58c5ec75b028a1c4a955f0d5d01a1656d33c   IDENTICAL
```

So my sharpest sentence in the original — "`68ddbe8` adds a CI gate that does not exist on GitHub" — was **false**. The gate is on `main`, it grew from 286 to 401 lines, and CI calls it. `wip-before-rebuild` is a pre-rebuild leftover: it is genuinely the only ref to those three SHAs, and nothing in it is lost work.

**Correct status:** the tag can be deleted without losing anything. It was nonetheless backed up to `origin/backup/rescue-0916/tag-wip-before-rebuild` before this was measured — harmless, and disclosed by the CEO as its own over-reach.

**Generalisable lesson for future sync audits of this repo:** `--not --remotes=origin` is the right test for "has GitHub seen this commit" and the *wrong* test for "would this work be lost". Any branch or tag flagged by the first test must be re-checked with `git cherry` before it is called lost work.
