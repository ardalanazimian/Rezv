### A design constraint for whoever builds axis 5

The guard's model of the CI database is not CI's database. Guard line 254 describes it as
`db push + apply-sql (exactly ci.yml:120-124)`. But `ci.yml:128` also runs
`prisma/test-schema-fixups.sql`, and the guard applies that file zero times.

That is harmless for CHECK constraints today, because the fixups only set defaults. For candidate A
it decides the answer:

- **Built with the fixups**, a defaults axis matches CI, but the fixups hide the very class they patch.
- **Built without them**, it reports every uuid PK default the fixups add, which is the
  "always red, so always ignored" failure the guard header warns about.

Both numbers are needed, and they are different claims.

### How to close each, cheapest first

Build the same two databases the guard builds. Build the CI one **with** the fixups. Then run one
query per candidate, sorted with `LC_ALL=C` and compared with `comm` in **both** directions:

```sql
-- A  defaults
SELECT table_name||'.'||column_name||' = '||coalesce(column_default,'∅')
  FROM information_schema.columns WHERE table_schema = 'public';
-- B  enum values
SELECT t.typname||'.'||e.enumlabel FROM pg_enum e JOIN pg_type t ON t.oid = e.enumtypid;
-- C  nullability, arrays excluded (already measured 2026-08-20)
SELECT table_name||'.'||column_name||' '||is_nullable
  FROM information_schema.columns WHERE table_schema = 'public' AND data_type <> 'ARRAY';
-- D  exclusion constraints
SELECT conrelid::regclass::text||' | '||pg_get_constraintdef(oid) FROM pg_constraint WHERE contype = 'x';
-- E  triggers
SELECT tgrelid::regclass::text||'.'||tgname FROM pg_trigger WHERE NOT tgisinternal;
```

**Control, per technique 21 in `ATTACKS.md`.** For each query, plant one known difference in the
prod database, such as dropping one default, and confirm the query reports it. A comparison that
has never gone red proves nothing about the axis.
