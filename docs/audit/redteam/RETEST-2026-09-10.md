### The correction, first, because it nearly became a false finding

I built a probe to prove `errorResponse()`'s unknown branch increments nothing, with the `P2024` branch three lines above it as the **control** — that one was given a counter yesterday, so it must move.

That test asserts `poolCount() >= before + 1` (`:115`) and it passes. **The counter works. My instrument was broken.**

**Cause: not established. I first wrote down a wrong one and it is retracted here.** I claimed the split came from `db-pool-exhaustion-contract.test.mts:38` importing `'../src/lib/metrics.ts'` **with** the extension while `errors.ts:3` imports `'./metrics'` **without**. **The refutation was already inside the paragraph that made the claim.** That very test imports *with* the extension and asserts the counter increments, and it is green. Had the extension split the instances, that assertion could not pass. I quoted the disproof and drew the opposite conclusion from it. The real trap in this repo is **alias versus relative** (`@/lib/…` against `./…`), not any difference in specifier form — a broader rule here would make the next session flinch at harmless differences, which is the opposite of useful.

So the honest record is: **four rounds were lost inside my own tooling and the cause is still unknown.** What is known is that the code is fine, my probe was not, and the control is what separated those two.

### One real thing, in the ambiguity class

`.github/workflows/ci.yml:447` — the e2e job installs with:

```
run: npm ci || npm install
```

`npm ci` is the command that installs *exactly* the lockfile. `npm install` is the command that is
allowed to resolve something else. The `||` means a failing `npm ci` — the usual cause being a
lockfile out of sync with `package.json` — is **swallowed**, and the job proceeds against a
dependency set nobody pinned. The job still gates, so this is not a fake-green; but **"e2e passed"
stops being "e2e passed on the pinned dependencies"**, and the difference only shows up on the day a
dependency changes behaviour.

It is the sibling of the rule already in the constitution about reading an exit code off the end of a
pipe: `||` discards a failure the same way, and here it discards the one that says *your lockfile is
wrong*. Minor, one line, and the fix — dropping `|| npm install` — is a decision for whoever owns CI,
not mine.
