## RT-09 — "why is the list a list?" · the unknown-error branch

**Verdict: the branch that catches instance six has no counter of its own, and no alert can tell a 500 from a 409. CONFIRMED — but not by the probe I built for it. Read the correction first.**

### The correction, first, because it nearly became a false finding

I built a probe to prove `errorResponse()`'s unknown branch increments nothing, with the `P2024` branch three lines above it as the **control** — that one was given a counter yesterday, so it must move.

**The control did not move either.** Repeated, isolated, and reproduced exactly:

```
typeof metrics.dbPoolTimeouts        object
v0                                   none
v1 after direct .inc()               1
errorResponse(P2024)   status=503    v2 = 1     ← branch ran, counter did not move
errorResponse(P2024) again           v3 = 1
```

Status `503` proves the pool branch executed — nothing else in `errorResponse` returns 503. So the reading was "the counter added yesterday is inert", which would have been a serious finding about the CEO's own fix.

**It was false, and the control is the only reason I know that.** The repo's own test, run against the live throwaway database:

```
npx tsx --test tests/db-pool-exhaustion-contract.test.mts     TEST_EXIT=0
ok 1 - P2024 — ته‌کشیدنِ استخرِ اتصال
# tests 2 · # pass 2 · # fail 0
```

That test asserts `poolCount() >= before + 1` (`:115`) and it passes. **The counter works. My instrument was broken.** Cause: `db-pool-exhaustion-contract.test.mts:38` imports `'../src/lib/metrics.ts'` **with** the extension while `errors.ts:3` imports `'./metrics'` **without** — and my probe's mixture of those two forms read a different module instance than the code wrote to. Four rounds spent inside my own tooling. Logged as a machine trap in `ATTACKS.md`.

**Had I skipped the control, this document would now claim the CEO shipped a dead counter.** That is the whole argument for controls, and it is worth more than the finding underneath it.

### What actually holds, on evidence that is not mine

The repo's own passing test states the finding better than my probe could:

- `:129` — `assert.equal(res.status, 500, 'فقط P2024 باید ۵۰۳ شود')`
- `:142` — `assert.equal(poolCount(), before, 'شمارنده نباید برای خطای نامربوط بالا برود')`

**An unrecognised error returns 500 and moves no dedicated counter — and that is asserted, deliberately, by a test that passes.** The behaviour is not an oversight; it is specified. `errors.ts:104` logs `خطای غیرمنتظره` and returns. The contrast inside one function is the argument: the *known* fifth instance was given `metrics.dbPoolTimeouts` at `:99`; the branch that will catch the *sixth* was given a log line.

### The part that is genuinely uncounted — the alert, not the counter

`httpErrors` **does** move, and it carries a `status` label (`metrics.ts:346-348`), so `rezervno_http_errors_total{status="500"}` exists as a series. **This corrects my own RT-06 from yesterday**, where I wrote that the P2028 patch "spent the only signal there was". Too strong: the series survives.

What does not survive is any alert that can see it:

```
grep -n 'status=~|status="5' observability/alerts.yml     → no matches
HighErrorRate (alerts.yml:22-25):
  sum(rate(rezervno_http_errors_total[5m])) / sum(rate(rezervno_http_requests_total[5m])) > 0.01
```

**No status filter anywhere in the file.** A 500 storm and a 4xx storm are the same alert, and every 4xx counts toward the same ratio. So the accurate statement is not "nothing counts instance six" — it is **"instance six is counted into the same bucket as ordinary client errors, and the last two fixes moved this exact class into that bucket on purpose"** (P2028 → 409, P2024 → 503). Each fix was right for the guest and each raised the noise floor that the next instance must clear before anyone notices.

### The decision package — for the CEO, not for me and not for whoever gets there first

**Recommended now, low risk:** a dedicated counter on the unknown branch, and one alert keyed on `status="500"`. A 500 has a near-zero baseline; a 409 does not. This makes the sixth instance announce itself on the day it first fires, and it is a few lines. It does not change any behaviour.

**Probably right, medium risk:** classify by *origin* rather than by code — all five instances so far were contention or infrastructure and all resolve to "retryable". Bounded work, changes responses.

**The real answer, and the one I am not taking:** invert the catch, so anything thrown inside the reservation transaction is a transaction failure unless proven otherwise. This ends the class instead of extending it. **It can also mask a genuine bug as a retryable conflict**, which is a product risk, not an engineering preference. It needs the CEO to accept that trade explicitly.
