## ⚠️ First, a retraction — I nearly filed a false finding

While running the full suite on the branch tree I hit **7 failures in
`points-redemption.integration.test.mts`** (`23502` NOT NULL on `points_ledger.id` via
`redeemPointsTx`). I reverted my own edits and re-ran on the untouched tree: **still 7
failures**. At that point the evidence said "pre-existing defect on a branch about to merge,"
and the README's headline claim of *1839/1839 green* looked false.

It was not. On a **destroyed-and-rebuilt** database at `main`, the same file is **20/20,
exit 0**.

The cause was my own database: it had been created once, migrated across two different
commits, and pushed through several runs — `prisma db push` had already refused with
`--accept-data-loss` warnings, which I should have read as "this DB is no longer the schema
you think it is." `test-schema-fixups.sql` adds `DEFAULT gen_random_uuid()` to `id` columns
that `db push` leaves bare, and my stale DB had drifted out from under it.

**Recording this deliberately.** "Reverting my changes and still seeing the failure" *felt*
like a controlled experiment and was not — both arms ran against the same poisoned DB, so the
control proved only that the poison was not mine. A red team that files this as a blocker
burns a day of someone else's work. The charter's "fresh database, always" is not hygiene
advice; it is the thing that separates a finding from an artifact.

## RT-18 — FAKEABLE — the loyalty guard detects a *spelling*, not a deduction

**This is the headline.** The RT-14 fix widened *where* the guard looks. It did not change
*what* it recognises, and the recogniser is a literal text match.

`tools/check-loyalty-promise.mjs:140-145` on `main`:

```js
const DEDUCTION_SHAPES = [
  /delta\s*:\s*-/g,                        // { delta: -x }
  /\$\{\s*-\s*[\w.]+\s*\}\s*::\s*int/g,   // ${-points}::int
];
const DEDUCTION_NAMES = /\bexpirePoints\b|\bdeductPoints\b|\bspendPoints\b|\bexpireStalePoints\b/g;
```

A deduction only registers if the source literally contains `delta: -`, or the raw-SQL form,
or one of four hardcoded function names. Hoist the negation into a variable and the guard sees
nothing.

### The attack — same directory, same semantics, one line moved

```ts
// api/src/app/api/v1/admin/points-sweep/route.ts
export async function sweepAgedPoints(_req: NextRequest) {
  const stale = await db.$queryRaw<Array<{ user_id: string; points: number }>>`
    SELECT user_id, SUM(delta)::int AS points FROM points_ledger
    WHERE created_at < now() - INTERVAL '1 year' GROUP BY user_id
  `;
  for (const row of stale) {
    const adjustment = 0 - row.points;                       // ← the whole attack
    await db.pointsLedger.create({
      data: { userId: row.user_id, delta: adjustment, reason: 'cleanup' },
    });
  }
  return NextResponse.json({ swept: stale.length });
}
```

| Tree state | Guard output | Exit |
|---|---|---|
| baseline (`main`, clean) | `✓ … هم‌داستان است` | **0** |
| **the file above** — real age-based expiry | `✓ وعده‌ی «امتیاز منقضی نمی‌شود» با مکانیزم هم‌داستان است` · `هیچ کسرِ سن/زمان‌محوری در api/src نیست (270 فایل اسکن شد)` | **0** 🔴 |
| **positive control** — same file, same directory, only `delta: adjustment` → `delta: -row.points` | ✗ violation reported | **1** |
| reverted | ✓ | **0** |

The control is what makes this a verdict rather than an opinion: the file **is** scanned (it
is one of the 270), the location **is** covered, the payload **is** detectable in its literal
form. The only variable that changed between exit 1 and exit 0 is whether the minus sign
appears next to the word `delta`.

**Why this is not a contrived bypass.** `const adjustment = 0 - row.points` is not obfuscation
— it is how a competent engineer writes a computed adjustment, especially once the amount
comes from a policy lookup, a config value, or a function return. Nobody has to be trying to
evade the guard. Note also that the guard prints `270 فایل اسکن شد` while saying nothing was
found, which reads as thorough coverage and is precisely the reassurance that makes it
dangerous.

**Who walks this by accident:** the same session as before — "admin can clear stale points" —
except now it passes the guard *and* looks like it was checked by a scope-corrected gate.

**What a real fix needs** (not my call — I only note that widening the regex is not it): the
guard has to reason about the *value* reaching `delta`, or the ledger has to make expiry
structurally impossible. A pattern list will always be one rename behind. Ideas: a
`pointsLedger.create` wrapper that requires a typed, enumerated `reason`, with the guard
asserting no age-based reason exists; or a DB-level CHECK rejecting negative deltas whose
reason is not in the allowed set. Both fail closed; the regex fails open.

# § 049 — SMS charge-once (`ad93943`), attacked and fixed

Taken at `rezv-48`'s request; it confirmed it would not touch the SMS path meanwhile, so
these fixes carry no collision risk. Three findings, all fixed here.

**What holds.** The core claim of 049 is real. Migration `087` is safe by construction — `job_id`
is a new nullable column, all existing rows are NULL, and Postgres treats NULLs as distinct in a
unique index, so the index cannot fail on existing data. The ordering choice (check → send →
charge) is documented in FIX-049 §3 with an honest cost table. On a fresh DB the three SMS suites
are **24/24, exit 0**.

## RT-19 — FIXED — the metric that justified the trade-off had no alert rule

FIX-049 §3 defends choosing "check → send → charge" by arguing the cost is platform money and
**«بی‌صدا نیست»** — not silent — citing `rezervno_sms_uncharged_total{template,reason}`.

The metric exists. **No alert rule referenced it.** `grep` over `observability/alerts.yml`
returned nothing.

This passes CI **by design**: `check-alert-metric-binding.mjs` deliberately treats "declared but
never alerted" as a warning, not an error — its header explains why (not every metric deserves an
alert, and hard-failing would grow an allowlist). That reasoning is sound in general and is
exactly why this one slipped: the guard cannot know that *this particular* counter is the
evidence a written trade-off leans on.

**Fixed:** `SmsUnchargedSends` — `sum(increase(rezervno_sms_uncharged_total[1h])) > 5`, `for: 10m`,
`severity: warning`. Threshold is deliberately **not** zero: this state is *expected* at the
balance boundary and 049 accepted it. What is not expected is it recurring. The annotation splits
the two reasons, because they mean different things — `insufficient_balance` is the accepted
trade; `charge_failed` is not normal and usually means a stale Prisma client (see RT-21).

## RT-20 — FIXED — "one charge per job" is not "one send per job"

**The evidence was already in 049's own test, read as a precondition instead of a cost.**
`sms-worker-charge-once.integration.test.mts:213`:

```js
await runWorker();
assert.equal(calls.get(to), 2, 'موضوعِ تست غایب است: reclaim اجرا نشد و job دوباره نرفت');
```

`calls` counts **real provider sends**. The test asserts the provider was called **twice** and
then asserts the balance moved **once** — and treats the 2 as confirmation that the reclaim
happened. It is also the whole finding: the guest received two SMS and the platform paid the
provider twice.

The reclaim path (worker crash or lease expiry) re-enters the handler, and `sendSmsNow` runs
**before** the charge is attempted. The charge then hits
`sms_transactions_job_id_key` and returns `already_charged`. Billing is correct. Nothing else is.

**And `already_charged` was the one outcome of `sendSmsCharged` with no signal at all** — no log,
no metric. Verified with `git grep`: it appeared only inside `sms-balance.ts` (3 occurrences, all
its own definition and returns) and had zero consumers. `charge_failed` and `insufficient` both
got a `log.error` and a `smsUncharged` increment; this one fell through to a bare return.

**This is RT-13's pattern again, and that is the part worth noticing.** Before 049, a reclaim
double-charged — and the extra debit was visible in the restaurant's own SMS history, where a
human would eventually query it. After 049 the billing is correct and the duplicate send became
*completely* invisible. Both fixes were right, and both made their residual failure quieter rather
than rarer. That is now three occurrences; it is a habit of this codebase, not a coincidence.

**Fixed:** new counter `rezervno_sms_duplicate_send_total`, a `log.error` at the
`already_charged` branch, alert `SmsDuplicateSend` (`increase[1h] > 0`, threshold zero — billing
is correct, so this counter is the only signal that a guest got two messages), and a new assertion
in 049's own reclaim test.

**What I did not fix, deliberately:** the duplicate *send* itself. Preventing it needs either a
provider-side idempotency key or a pre-send claim marker, and a pre-send marker reintroduces the
exact failure 049 removed (a crash between marker and send loses the message silently). That is a
design decision with a real trade, not a patch. This fix makes the duplicate **visible**; it does
not pretend it is gone.

## RT-21 — FIXED — `test-env-up.sh` leaves a stale Prisma client, and it fails *open* on money

`tools/test-env-up.sh` — the repo's documented way to stand up the test environment — ran
`npx prisma db push --skip-generate` and never regenerated the client. In CI this is harmless:
every job runs `npm ci`, whose `postinstall: prisma generate` hook rebuilds it. Locally,
`node_modules` persists across branches.

So: `npm ci` on one branch, switch to a branch that changed `schema.prisma` (here `087`, which
added `sms_transactions.job_id @unique`), run the suite. The database is correct. The client is
stale.

**Why this is more than a papercut — the symptom is a money bug.** `sendSmsCharged` sends first,
then charges. The stale client throws `Invalid tx.smsTransaction.findUnique() invocation`, the
`catch` swallows it, and the outcome is `sent` / `charge_failed`. Observable result: **SMS
delivered, balance untouched.** That is indistinguishable from a revenue-leak defect in the money
path.

I diagnosed it as a defect **twice today** before reading the Prisma error text. Any session doing
what I did — switch branch, run tests — hits it, and the natural conclusion is "049 doesn't charge."

**Fixed:** `npx prisma generate` added to `test-env-up.sh` before `db push`, with the reasoning
inline so the next reader does not delete it as redundant.

## Two near-misses, recorded because the discipline is the deliverable

Both of today's false leads had the same shape: **a real-looking failure in a money path, caused
by my own environment.**

1. **Poisoned DB** → 7 `points-redemption` failures. I reverted my own changes, saw the failure
   persist, and read that as a control. It was not — both arms ran against the same bad DB.
2. **Stale Prisma client** → 2 `sms-worker-charge-once` failures, surfacing as "SMS sent,

In both cases the honest-looking move (file the finding, it reproduces on a clean tree) would have
been wrong, and would have cost another session a day defending working code. What caught them was
the same thing each time: **rebuild the environment from scratch, then read the actual error text
instead of the assertion message.** The assertion says what was expected; only the error says why.

A red team that files false blockers is worse than no red team — it trains people to discount real
ones. Recording these two by name so the next session recognises the shape.
