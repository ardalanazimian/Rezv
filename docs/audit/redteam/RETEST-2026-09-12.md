## RT-13 — BLIND — a real double charge is invisible after the fix that "closed" it

**Claim under test** (bundle `README.md`, patch `0005`): *"شارژ دوباره‌ی بیعانه — قفل ردیف رزرو با
`FOR UPDATE` … به‌علاوه ایندکس یکتای جزئی `payments_one_success_per_reservation` (مهاجرت ۰۸۶)"*.

### The prevention half is real, and I proved it fires

Raw output, live DB, inside a rolled-back transaction:

```text
=== A) second SUCCESS row for same reservation (the shape 086 blocks) ===
ERROR:  duplicate key value violates unique constraint "payments_one_success_per_reservation"
DETAIL:  Key (reservation_id)=(11111111-1111-1111-1111-111111111111) already exists.
```

`api/tests/payments.integration.test.mts` on a fresh DB: **20 tests, 20 pass, 0 fail, exit 0.**

### The detection half is dead — four legs, each measured

**1. What the patched code writes for a genuine double charge.**
`api/src/app/api/v1/payments/callback/route.ts:128` writes the second, *really paid* attempt as
`status: 'failed'` + `failReason: REFUND_REQUIRED…` + the real gateway `refId`. The suite pins
exactly this shape (`payments.integration.test.mts:426-429`): `pA.status === 'failed'`, `failReason`
matches `/^REFUND_REQUIRED/`, `refId === 'REF-A'`, `verifiedAt` set. Money left the guest's account;
the row says `failed`. The code's own comment is honest about this — it notes `PaymentStatus` has no
"awaiting refund" value and `failReason` is the only free-text field available.

**2. The only documented detection query cannot match that shape.**
Migration `086`'s header instructs the operator to run:

```sql
SELECT reservation_id, count(*), array_agg(id ORDER BY created_at)
FROM payments WHERE status = 'success'
GROUP BY reservation_id HAVING count(*) > 1;
```

Run against exactly the state from leg 1 — raw output:

```text
=== C) MIGRATION 086 DOCUMENTED DETECTION QUERY, run on that exact state ===
 reservation_id | n
----------------+---
(0 rows)

=== D) what is actually in the table (money taken twice) ===
 status  |       fail_reason       | ref_id
---------+-------------------------+--------
 success | -                       |
 failed  | REFUND_REQUIRED: پرداختِ | REF-A
```

**3. After `086` applies, that query can never return a row again — by construction.**
The index makes two `success` rows impossible (leg 1's `ERROR`). The query looks for two `success`
rows. It is sound as the *pre-deploy* check the header calls it; the defect is that it is also the
**only** detection anyone wrote down.

**4. Nothing else sees it.**

- **No `audit()`.** The route imports `db`, `zarinpal`, `ratelimit`, `logger`, `errors`, `schemas`,
  `public-urls`, `api-metrics` — no audit import, though `CLAUDE.md` requires `audit(...)` for
  reservation-cycle money operations.
- **`REFUND_REQUIRED` has no consumer anywhere in the repo.** `git grep` across the whole tree,
  excluding the route and its own test, returns nothing. Positive control: the same grep against the
  route returns its 3 hits, so this is not a false null.
- **The only payment alert cannot fire.** `PaymentEndpointErrors` (`observability/alerts.yml:281`)
  is a ratio over `rezervno_http_errors_total`, documented at `api/src/lib/metrics.ts:86` as
  *"تعداد پاسخ‌های خطا (۴xx/۵xx)"*. The duplicate path ends at `redirectToApp(...)` → **HTTP 302**
  (`route.ts:33`). A 302 is not 4xx/5xx. The alert is **structurally incapable** of firing here.

The single trace is one `log.error` line.

### Net

Before this patch a double charge left two `success` rows — ugly, but the documented query found it.
After it, the same event leaves one `success` + one `failed`, and every written-down detector returns
empty. **The fix made the failure quieter, not rarer.** Anyone who accepted "deposit double-charge:
closed" should know the residual case is now unobservable.

**Who walks this by accident:** an operator running the `086` pre-deploy check, reading `(0 rows)`,
and reporting "no double charges" — true of history, meaningless about the future.

### Reproduction payload

The scratch branch carries no commit, because the charter requires the tree be left clean. This is
the whole attack:

```ts
// api/src/app/api/v1/admin/expire-points/route.ts
export async function expireStalePointsForAll(req: NextRequest) {
  await requireAdmin(req);
  const stale = await db.$queryRaw<Array<{ user_id: string; points: number }>>`
    SELECT user_id, SUM(delta)::int AS points FROM points_ledger
    WHERE created_at < now() - INTERVAL '1 year' GROUP BY user_id
  `;
  for (const row of stale) {
    await db.pointsLedger.create({ data: { userId: row.user_id, delta: -row.points, reason: 'cleanup' } });
  }
  return NextResponse.json({ expired: stale.length });
}
```
