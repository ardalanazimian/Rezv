## RT-05 — the fifth instance: `P2024`, and the arithmetic makes it likelier than the four before it

You asked for the next error that can leave `createReservation` / `createWalkin` raw. It is
**`P2024` — "Timed out fetching a new connection from the connection pool."**

- Handled **nowhere**: `grep -rn 'P2024|P1001|P1002|P1008|P2037|57014|55P03|53300' api/src api/tests tools` → **no matches**.
- Not in `isSerializationError` (`40001` · `40P01` · `P2034`), not in `isConflictError` (`23P01` · `40001` · `40P01`), not `isTransactionTimeoutError` (`P2028` only).
- So it reaches `throw e` and `errors.ts:69` returns `INTERNAL` / **500**.

**The arithmetic is the argument.** `db.ts:52` sets `connection_limit=10`; `db.ts:56` sets
`pool_timeout=10`; the reservation transaction holds its connection for up to `timeout: 10_000`
(`reservations.ts:407`, and `:1005` for walk-in). Eleven concurrent booking attempts on one instance
and the eleventh waits ten seconds for a connection it will not get, then throws `P2024`.

**P2028 needs one transaction to be slow. P2024 needs ten to be ordinary.** A Friday-night rush is
the second condition, not the first — so the instance you have not patched is the more probable one.

**Why your class-based guard cannot catch it, and this is the general lesson.**
`tx-timeout-error-contract.test.mts:166` asserts the thrown error's code is in
`{TABLE_CONFLICT, SLOT_FULL, CONCURRENCY_RETRY, SLOT_LOCK_TIMEOUT}`. That assertion **is**
class-based, and you were right about it. But a test is two axes, and only one of them was made
class-based: the **stimulus** is a single staged row-lock race. A pool exhaustion never occurs in
that scenario, so the class-based assertion is never handed the fifth instance to judge. **The
assertion generalises; the stimulus does not.** This is attack #19 in `ATTACKS.md` — the author picks
the axis — and it is the same shape as FG-10 this morning.

## RT-06 — your guess was right, and the patch is worse than invisible

**It is not neutral invisibility — the patch spent the only signal there was.** Before `38a9570` a

which are indistinguishable from ordinary double-booking rejections. The user-facing change is right;
the observability change is a regression, and it is the kind that is only discovered during the
incident it hides. Adding a labelled increment on the three uncounted exits is small and should ride
along with the `P2024` fix.
