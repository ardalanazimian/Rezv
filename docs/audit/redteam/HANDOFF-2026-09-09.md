## The question worth taking first tomorrow — "why is the list a list?"

Five instances of one class have now been patched, each **after** it happened: raw `ioredis` (08-14), `SLOT_LOCK_TIMEOUT` (08-19), `40P01` deadlock (08-25), `P2028` (09-09 morning), `P2024` (09-09 afternoon, predicted by RT-05 before it was observed). The sixth will arrive the same way unless the shape changes.

**The shape is this:** `errors.ts` ends with an unconditional fallback — anything that is not an `ApiError` becomes `INTERNAL` / 500. So the default answer to *"I do not recognise this error"* is **"tell the user the server is broken"**, and every fix so far has been to move one more code from the unknown pile to the known pile. The pile is unbounded; the list will never be finished, and its length is a measure of how many times we were surprised, not of how much is covered.

**The question to ask is not "what is the sixth code?" It is: why is `unrecognised ⇒ 500` instead of `unrecognised ⇒ triage`?** Concretely, three things to look at, in this order:

1. **Is `500` even right for this class?** Every instance so far has been *contention or infrastructure*, where the honest answer to the guest is "try again in a moment" — `409`/`503`, which the CEO chose for `P2024`. If the whole class resolves to "retryable", the fallback could classify by *origin* (came out of a transaction? a pool? a lock?) rather than by *code*, and the list stops growing.
2. **What does the unknown branch cost us in evidence?** `errors.ts:68` logs `خطای غیرمنتظره` and returns. There is **no counter on the unknown branch.** Add one and the sixth instance announces itself in production the day it first fires, instead of being discovered by a user report weeks later. This is the cheapest item on this page and it is not a guess — it is the same attack #20 that produced RT-06.
3. **Ask the question of the `catch`, not the fallback.** The five instances all escaped from *inside* `createReservation`/`createWalkin`'s catch blocks, which enumerate predicates. A catch that enumerates is a list by construction. Inverting it — "anything thrown from inside this transaction is a transaction failure unless proven otherwise" — is the change that ends the class. **It is also the riskier change**, because it can mask a genuine bug as a retryable conflict. That trade-off is a CEO decision and should be escalated as a decision package, not decided by whoever gets there first.

**My honest position:** item 2 should be done regardless and immediately; item 1 is probably right; item 3 is the real answer and needs someone senior to accept the risk. I did not get to any of them.
