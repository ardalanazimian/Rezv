> دامنه: فقط پنلِ **company**. پنل‌های business و customer روی OTP ماندند.

## چرا این کار انجام شد

ترانسپورتِ ملی‌پیامک با `400` و پیامِ «مستلزم تنظیم و تأیید مدیر» پاسخ می‌دهد،
و `OTP_DEV_MODE` در production استثنا می‌دهد. یعنی **هیچ راهی برای ورود به
پنلِ شرکت نمانده بود**.

TOTP (RFC 6238) کاملاً **آفلاین** است: یک رازِ مشترک و ساعتِ سیستم. هیچ
درخواستی به `accounts.google.com` نمی‌رود و هیچ OAuthی اضافه نشد — دقیقاً به
این دلیل که وابستگی به یک سرویسِ بیرونی یعنی روزی که قطع شود، از پنلِ خودمان
قفل بیرون می‌مانیم.

## فازِ ۱ الف — پیش‌نیاز: نتیجه‌ی کوئریِ زنده

سه یافته، هر سه با کوئریِ واقعی نه حدس:

### ۱. `PLATFORM_ADMIN_TENANT_ID` خالی است

```
.env:16   PLATFORM_ADMIN_TENANT_ID=
```

یعنی مسیرِ ورودِ رمزِ **موجود** هم امروز رویِ fail-closedِ خطِ ۴۷ می‌ایستد:
«پنل شرکت پیکربندی نشده است». ورودِ ادمین مستقل از پیامک هم کار نمی‌کرد.

### ۲. ردیفِ ادمینِ پلتفرم وجود ندارد

```sql
select (select count(*) from staff) staff_all,
       (select count(*) from staff where role='owner') owners,
       (select count(*) from tenants) tenants;

 staff_all | owners | tenants
         4 |      2 |       2
```

دو `owner` هست ولی چون تنانتِ پلتفرم تعریف نشده، هیچ‌کدام ادمینِ پلتفرم نیستند.

### ۳. ⚠️ دیتابیسِ dev از اسکیما عقب است

```
ستون‌های staff در DBِ dev:
  id · tenant_id · phone · name · role · is_active · restaurant_id
```

نه `username`، نه `password_hash`، نه `created_at`. تأییدِ مستقل:

```sql
select count(*) from _prisma_migrations;
ERROR:  relation "_prisma_migrations" does not exist
```

جدولِ مهاجرت‌ها **اصلاً وجود ندارد** — این DB با `prisma db push` بوت‌استرپ
شده و از آن روز به‌روز نشده (حدود ۷۵ مهاجرت عقب).

مقایسه با DBِ تست که سوئیت رویش اجرا می‌شود:

```
ستون‌های staff در DBِ تست:
  … created_at · username · password_hash · password_updated_at   ✅
```

پس تست‌ها رویِ اسکیمای درست اجرا می‌شوند و این ناسازگاری را نمی‌بینند.

> **حکم:** هیچ‌کدام از پیش‌نیازها برقرار نبود ⇒ اسکریپتِ سوم (`admin-provision`)
> **لازم** شد، نه اختیاری.

## فازِ ۱ ب — عاملِ سوم رویِ مسیرِ موجود

### هیچ مسیرِ موازی ساخته نشد

فازِ ۰ نشان داد `POST /api/v1/auth/admin/login` از قبل وجود دارد. عاملِ سوم به
**همان** اضافه شد.

| الزام | وضعیت |
|---|---|
| ⭐ `principal` خطِ ۴۴ | **اصلاً لمس نشد** — همان `{sub, kind:'staff', tenantId, role:'owner'}` |
| ⭐ `admin-auth.ts` | **اصلاً لمس نشد** |
| `ADMIN_LOGIN_ENABLED` پیش‌فرض خاموش | ✅ خاموش = رفتارِ امروز بایت‌به‌بایت |
| روشن ولی راز نیست → fail-closed | ✅ ورود ممنوع، نه بازگشتِ بی‌صدا به دوعاملی |
| پنجره حداکثر ±۱ گام | ✅ `WINDOW_STEPS = 1` |
| ضدِ replay در Redis | ✅ کلیدِ گام‌محور، `SET NX` با TTL دقیقاً به‌اندازه‌ی پنجره |
| مقایسه‌ی constant-time | ✅ `validate()` کتابخانه (طولِ ثابت، `delta` برمی‌گرداند) |
| `adminTotpLogin` هم‌الگوی `passwordLogin` | ✅ هر دو بُعد IP و username، ۵ در ۱۵ دقیقه |
| پیامِ یکسان برای هر سه شکست | ✅ همان `Err.invalidCredentials` مسیرِ رمز |
| audit رویِ هر تلاش | ✅ موفق و ناموفق، با IP و نتیجه‌ی TOTP |

### نقطه‌ی مهاجرتِ آینده

راز فعلاً از env با جفتِ `ADMIN_TOTP_USERNAME` / `ADMIN_TOTP_SECRET`. اگر
`username`ِ ارسالی با صاحبِ راز یکی نباشد → همان ۴۰۱ِ عمومی.

⚠️ **تنها نقطه‌ای که راز را پیدا می‌کند** تابعِ `secretFor()` در
`lib/admin-totp.ts` است. روزی که چند ادمین شد و راز به ستونِ
`staff.totp_secret` مهاجرت کرد، فقط بدنه‌ی همان یک تابع عوض می‌شود؛ بقیه‌ی
ماژول و کلِ route دست‌نخورده می‌ماند. **هیچ مهاجرتی امروز زده نشد.**

### تصمیم‌های فنی (طبقِ سه انتخابِ تأییدشده)

| انتخاب | چرا |
|---|---|
| `otpauth` | نه پیاده‌سازیِ خانگی — base32 decode جای باگ‌خیزی است |
| `scrypt`ِ موجودِ `password.ts` | Argon2 کامپایلِ بومی می‌خواهد، همان ریسکی که تازه در ایمیجِ داکر بستیم |
| اعتبارنامه در DB | خطِ ۵۹ِ `admin-auth` که نقش را از DB می‌خواند یک **خاصیتِ امنیتی** است: هویتی که با غیرفعال‌کردنِ staff قابلِ ابطال نباشد بدتر از مشکلی است که حل می‌کند |

## فازِ ۳ — UI

فیلدِ سوم به فرمِ رمزِ **موجود** اضافه شد، نه تبِ تازه.

⚠️ **اگر قابلیت خاموش باشد، فیلد اصلاً در DOM ساخته نمی‌شود** — نه
`display:none`. دلیلش یک شکستِ واقعیِ همین مخزن است: یک عنصرِ مخفی با
`display:flex` دور زده شد. چیزی که رندر نشود قابلِ دور زدن نیست.

چون پنل استاتیک است و `process.env` را نمی‌بیند، تصمیم باید سمتِ سرور گرفته
شود. یک `GET /api/v1/auth/admin/login` سبک اضافه شد که فقط
`{ totp_required: boolean }` برمی‌گرداند. هر چهار نقطه‌ی رندرِ فرم (ورودِ اول،
خروج، انقضای نشست، بازگشت از OTP) از `loadAdminLoginForm()` عبور می‌کنند که
پرچم را **پیش از** رندر می‌گیرد.

> این نشتِ اطلاعات نیست: روشن‌بودنِ دوعاملی رازِ امنیتی نیست — مهاجم در اولین
> تلاش هم می‌فهمید. رازِ واقعی `ADMIN_TOTP_SECRET` است که هرگز بیرون نمی‌رود.

a11y و رفتار: `inputmode="numeric"` · `autocomplete="one-time-code"` ·
`maxlength=6` · `aria-describedby` · زنجیره‌ی Enter از نام‌کاربری → رمز → کد →
ارسال · پس از شکست کد پاک و فوکوس برگردانده می‌شود (کدِ مصرف‌شده دیگر معتبر
نیست).

## راه‌اندازی

### ۱. مقادیر `.env`

```bash
PLATFORM_ADMIN_TENANT_ID=<از مرحله‌ی ۲ می‌آید>
ADMIN_LOGIN_ENABLED=true
ADMIN_TOTP_USERNAME=<نامِ کاربری، حروفِ کوچک>
ADMIN_TOTP_SECRET=<از مرحله‌ی ۳ می‌آید>
```

⚠️ اگر `ADMIN_LOGIN_ENABLED=true` باشد ولی دو تای بعدی خالی، ورود **ممنوع**
می‌شود — عمداً.

### ۲. سه مرحله

```bash
# اول — رمز (دو بار تایپ، اکو خاموش؛ خودِ رمز هیچ‌جا ثبت نمی‌شود)
node tools/admin-hash-password.mjs

# دوم — ساختِ ادمین؛ PLATFORM_ADMIN_TENANT_ID را چاپ می‌کند
node tools/admin-provision.mjs myadmin 'scrypt$32768$8$1$...'

# سوم — رازِ TOTP؛ QR را در ترمینال می‌کشد
node tools/admin-totp-secret.mjs myadmin
```

**اسکنِ QR:** Google Authenticator یا Aegis را باز کنید → افزودنِ حساب →
اسکنِ QR. اگر اسکن نشد، کلیدِ base32 را دستی وارد کنید (Time-based, SHA1,
۶ رقم, ۳۰ ثانیه). اسکریپت **کدِ همین لحظه** را هم چاپ می‌کند: اگر اپ همان عدد
را نشان داد، اسکن درست بوده.

### ۳. آزمودنِ اولین ورود

```bash
curl -s http://localhost:3000/api/v1/auth/admin/login
# {"totp_required":true}

curl -s -X POST http://localhost:3000/api/v1/auth/admin/login \
  -H 'content-type: application/json' \
  -d '{"username":"myadmin","password":"<رمز>","totp":"<۶ رقم از اپ>"}'
```

موفق = JSON با `access` و `refresh` و `admin`.
شکست = `401 INVALID_CREDENTIALS` — **همان پیام** برای رمزِ غلط، کدِ غلط، و
کاربرِ اشتباه.
