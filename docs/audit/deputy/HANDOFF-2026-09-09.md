### ⚠️ ADDENDUM 2026-09-10 — two numbers in this file went stale in under 24 hours

**Both were correct when written, and both would now cause a wrong diagnosis.** That is the point of
this note more than the values are.

**1. The Redis port moved: `56379` → `16379`.** Corrected in the block above rather than only noted,
because that block is something people copy, and a dead value inside a copy-paste recipe is worse
than no recipe.

The cause is worth carrying because it does not look like what it is (diagnosed by the CEO session,
verified independently here): Windows had **reserved** the range `56316–56415`, so `docker start`
failed with *"an attempt was made to access a socket in a way forbidden by its access permissions."*
The port was **not occupied** — binding was **forbidden**. From outside, that is indistinguishable
from "the service is broken", and it is the same family as every other trap in this repo: **an
artefact read as a behaviour.** `netsh … excludedportrange` is what separates them.

**Verified here, not accepted on report:** `docker ps` shows `0.0.0.0:16379->6379/tcp`; a host TCP
connect to `16379` succeeds while `56379` gives `ECONNREFUSED`. And I sent a real `PING` over the
socket instead of stopping at "something answered" — the reply was `+PONG`, so it is genuinely
Redis. Per the standing rule: *"something answers on port X" is not "my server answers on port X."*
**`redis-cli ping` from inside the container proves nothing about the host mapping** — test from the host.

**2. `72` tables became `73`** — `otp_request_windows`, from `api/prisma/sql/083-otp-request-window.sql`.

**That migration closes E-003, the escalation I raised on 09-09.** I asked whether a transient Redis
blip may reset a per-phone OTP ceiling to zero on an auth path. The founder answered by moving the
ceiling **out of Redis into Postgres** (`217ac1f`). That does not mitigate the fail-open window — it
**removes it by construction**, since a Redis outage cannot reset a counter that no longer lives
there. **The retry was a mitigation; this is the decision.** Recorded so nobody reopens it.

**What this addendum is actually about:** every environment value in this file is a measurement with
a timestamp, not a constant. Re-read `docker ps` and the table count at the start of each session —
and if your number disagrees with this file, **this file is the one that is wrong**.

**`npm test` may refuse to start** — its `pretest` runs `tools/check-runner-completeness.mjs`, which
fails if any `*.test.mts` on disk is not imported in `_all.runner.mts`. That is directive 018's guard
working correctly, and it fires on *another session's* half-finished file, not on a real problem.
When that happens, `npx tsx --test tests/_all.runner.mts` runs exactly the same set (an unimported
file never executes either way) — **that bypasses the check, not the tests, and you should say so.**

## 4. Things that live only in this session — hypotheses, dead ends, and one method

**Dead end I hit, so nobody repeats it:** I tried to prove the `rateLimitFallback` counter moves by
reading it from a probe that imported `@/lib/metrics`. It read **0 → 0 while the fallback
demonstrably fired**, and I nearly filed "labelled counters do not record" — a false defect report
against working code. Cause: **`'./metrics'` and `'@/lib/metrics'` resolve to two separate module
instances under `tsx`**, each with its own Counter and its own values Map.
**The trap is alias-vs-relative, NOT any difference in specifier** — two *relative* imports of one
module share an instance (the CEO verified this independently by deleting an `inc` and watching its
test go red, which is impossible across separate instances). Full write-up: `ORDER-004…md` §A3.
