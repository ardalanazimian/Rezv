## ۲. ریشه و کلاس

**ریشه:** `sendSmsNow` خروجی نداشت (`void`)، پس «رفت» و «نرفت» از بیرون یکی بودند؛ و handlerِ worker
**پیش از** دانستنِ آن، و بدونِ کلیدِ job، کسر می‌کرد.

**کلاس — عوارضِ جانبیِ پولی پیش از تأییدِ اثر، در کاری که دوباره اجرا می‌شود.** سه عضو، که ۰۴۹ دوتایش را گفت:

| عضو | چرا رخ می‌داد |
|---|---|
| retry پس از شکستِ شبکه → کسرِ دوم | `sendSmsNow` throw می‌کند، `failJob` retry، handler دوباره `consumeSms` |
| reclaim پس از کرش → کسرِ دوم | `d64d84a` jobِ رهاشده را درست برمی‌گرداند؛ handler برای اجرای دوباره نوشته نشده بود |
| **ردِ ارائه‌دهنده → کسر بدونِ ارسال** (۰۴۹ نگفته بود) | `sendSmsNow` روی `RetStatus !== 1`، «پیکربندی‌نشده»، «بی‌خط» و «بی‌bodyId» **throw نمی‌کند**؛ job کامل و پول رفته |

**sweep** (با کنترلِ مثبت): تنها دو محلِ کسرِ موجودیِ پیامک در `api/src` همان دو‌تا بودند — `worker.ts` و
`sendDirectFallback`. مسیرِ اضطراری همان نقص را داشت (رد و شکستِ شبکه هر دو کسر می‌کردند). روی
`fix/verified-findings-2026-09` (#86) همان دو محل **بی‌تغییر**اند و آن شاخه به هیچ‌یک از فایل‌های این رفع دست
نمی‌زند (جز بلوکِ دیگری از `schema.prisma`).

⚠️ **یک null دروغین در همین sweep گرفته شد:** `git grep … origin/fix/… -- api/src` روی آن شاخه **صفر** داد در
حالی که `consumeSms(` آنجا هست. کنترلِ مثبت نشانش داد؛ علت تبدیلِ مسیرِ Git Bash بود (`MSYS_NO_PATHCONV`).

## ۳. تغییر — و انتخابِ ترتیب، با هزینه‌اش

۰۴۹ دو شکل را درست دانست. **«چک ← ارسال ← کسرِ کلیددار»** انتخاب شد:

| | چک ← ارسال ← کسر (انتخاب‌شده) | کسر ← ارسال ← بازپرداخت |
|---|---|---|
| شکستِ شبکه / retry | هیچ اعتباری گرفته نشده | اعتبار در طولِ retryها گرفته می‌ماند |
| رد / پیکربندی‌نشده | کسر نمی‌شود | بازپرداختِ صریح لازم است |
| jobی که با reclaim به `dead` برسد | چیزی برای بازپرداخت نیست | **قلابِ بازپرداخت در SQLِ reclaim لازم است، وگرنه اعتبار بی‌بازگشت می‌سوزد** |
| `sms_total_sent` | فقط با پذیرش | باید جدا نگه داشته شود |
| **هزینه** | **در مرزِ موجودی، workerِ هم‌زمان می‌تواند پیامی بفرستد که دیگر قابلِ‌کسر نیست** | ارسالِ فراتر از موجودی ممکن نیست |

هزینه‌ی انتخاب‌شده **پولِ پلتفرم** است (حداکثر به تعدادِ workerهای هم‌زمان در لحظه‌ی تمام‌شدنِ اعتبار)، نه
صورت‌حسابِ غلطِ رستوران — و **بی‌صدا نیست**: `rezervno_sms_uncharged_total{template,reason}`. عکسش پولِ
رستوران را در یک مسیرِ کرش بی‌بازگشت می‌سوزاند. اگر بازبین این معامله را برعکس می‌بیند، همین جدول محلِ بحث است.

| فایل | چه |
|---|---|
| `api/src/lib/sms.ts` | `sendSmsNow` حالا `SmsSendResult` برمی‌گرداند (شبکه همچنان throw). **`sendSmsCharged`**: تنها قاعده‌ی پول — worker و مسیرِ اضطراری هر دو از همین‌جا. شکستِ خودِ کسر پس از ارسالِ موفق throw نمی‌کند (throw = retry = پیامِ تکراری به مهمان)؛ شمرده می‌شود |
| `api/src/lib/sms-balance.ts` | `debitSms` تنها مسیرِ SQLِ کسر؛ `consumeSms` (رفتارِ قبلی، بدونِ کلید) و `chargeSmsForJob` (کلیددار) هر دو روی آن. `hasSmsBalance` فقط می‌خواند. `P2002` روی ایندکس ⇒ `already_charged` |
| `api/src/lib/worker.ts` | handler `job` را می‌گیرد و `sendSmsCharged(p, { jobId: job.id })` می‌زند؛ نتیجه در `jobs.result` می‌نشیند |
| `api/prisma/sql/087-sms-transactions-job-id.sql` + `schema.prisma` | `sms_transactions.job_id` + ایندکسِ یکتای `sms_transactions_job_id_key` (NULLها متمایزند؛ بدونِ FK به `jobs`) |
| `api/src/lib/metrics.ts` | `rezervno_sms_uncharged_total` |
| `api/src/lib/queue.ts` | `JOB_WORST_CASE_MS`: دو رفت‌وبرگشتِ DB → **سه** (چک، کسر، complete). اجاره ۲۵ → ۳۳ دقیقه. عدد مشتق است، نه سلیقه |
| `api/tests/sms-worker-charge-once.integration.test.mts` | **تازه** — ۶ تست (۴ ادعای پول + ۲ کنترل) |
| `api/tests/sms-queue-fallback-balance.integration.test.mts` | یک تست **بازنویسی** شد، یک تست افزوده، یک assertion افزوده (§۵) |

## ۵. تستی که نقص را پین می‌کرد — تغییر کرد، حذف نشد

`sms-queue-fallback-balance`: «صف که بیفتد، مسیرِ اضطراری دقیقاً یک اعتبار کسر می‌کند» کسر را روی حالتِ
**پیکربندی‌نشده** تأیید می‌کرد و `smsFailed{not_configured}+1` را «پیام واقعاً تلاش به ارسال شده» می‌خواند — یعنی
دقیقاً اعتبار برای پیامی که نرفت. حالا ارائه‌دهنده (stubِ محلی) می‌پذیرد و کسر پس از آن ادعا می‌شود. قرمزِ پیش از
رفع برای دو ادعای تازه‌ی همین فایل، روی کدِ اصلی (فایل‌های `src` موقتاً از `HEAD`، سپس بازگردانیِ `cmp`‌شده):

```text
FALLBACK_TEST_EXIT_ON_ORIGINAL_CODE=1   tests 7 · pass 5 · fail 2
  ارائه‌دهنده رد کند → مسیرِ اضطراری هیچ اعتباری کسر نمی‌کند         2 !== 3
  شکستِ ارسال در مسیرِ اضطراری … نباید اعتبار بسوزاند                 3 !== 4
```

## ۶. آنچه **وارسی نکردم**

- **CIِ لینوکس.** همه ویندوز است. `tools/check-schema-drift.sh` (jobِ `schema-drift`) نیازِ `psql` روی PATH دارد و اجرا
  نشد؛ همتای درون‌سوئیتش (`schema-drift.integration`) سبز است.
- **ارائه‌دهنده‌ی واقعی.** همه stubِ محلی است. پاسخِ خامِ ملی‌پیامک برای «پذیرفته» همان قراردادی است که
  `meliAccepted` از قبل داشت؛ آن را عوض نکردم و دوباره نسنجیدم.
- **مسابقه‌ی واقعیِ دو worker.** تستِ مرزِ موجودی آن را با اثرِ جانبیِ stub شبیه‌سازی می‌کند، نه با دو process.
  ایندکسِ یکتا را زیرِ دو اجرای **هم‌زمانِ** یک job مستقیم نزدم؛ مسیرِ `P2002 → already_charged` با کد خوانده شد.
- **`reason: 'campaign'`** برای همه‌ی پیامک‌های worker — حتی تأییدِ رزرو. از قبل همین بود؛ دست نزدم. تاریخچه‌ی
  پیامکِ رستوران آن را «کمپین» نشان می‌دهد. نقصِ کوچکِ برچسب، نه پول.
- **سایر handlerها** (`email`, `push`, `webhook`) — پول ندارند؛ اجرای دوباره‌شان at-least-once است و بررسی نشد.
- **بازپرداختِ تاریخی.** اگر دیتابیسِ تولیدیِ با رستورانِ واقعی وجود دارد، کسرهای اضافه‌ی گذشته آنجا مانده‌اند.
  ۰۴۷ می‌گوید کاربرِ واقعی نیست؛ اگر هست، تصمیمِ پول با مالک است.
