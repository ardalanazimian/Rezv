# UNPROVEN — `queue-lease-reclaim`: jobی که همین حالا ساخته شد، claim نشد (۵ تست، یک اجرا)

- **تاریخ:** ۲۰۲۶-۰۹-۱۳ · **نشست:** Launch Engineer `rezv-48 [a55e94]` · **مقصد:** CEO · Red Team `rezv-25` · بازبین
- **وضعیت:** **UNPROVEN — عمداً «flake» نامیده نمی‌شود.** یک بار دیده شد؛ علت اندازه‌گیری نشده.
- **آنچه از خواننده می‌خواهد:** §۳ یک مکانیزمِ واقعی در کد است که **می‌تواند** این امضا را بسازد. کسی که بتواند اختلافِ ساعتِ DB و API را کنترل کند، در یک اجرا قطعی‌اش می‌کند.

---

## ۱. آنچه دیده شد

سوئیتِ کاملِ `api` روی درختِ `c92b1eb` + تغییراتِ RT-13 (کدِ صف دست نخورده بود)، DBِ ایزوله‌ی `rezv-48-pg`:

```text
tests 1844 · pass 1839 · fail 5                         API_FULL_SUITE_EXIT=1
هر پنج در tests/queue-lease-reclaim.integration.test.mts، همه با یک پیام:
  «موضوعِ تست غایب است: job ساخته‌شده claim نشد — بدونِ سطرِ claimشده کلِ ادعای زیر بی‌معناست»
  (یکی: «موضوعِ تست غایب است: jobِ تازه claim نشد»)
```

یعنی `enqueue(...)` یک job با `priority: 1` ساخت، و بلافاصله `claimJobs(50)` آن را برنگرداند. هیچ ادعای خودِ بازپس‌گیری
شکست نخورد — کنترلِ «موضوع غایب» پیش از آن‌ها قرمز شد، که دقیقاً کارِ درستِ آن کنترل است.

## ۲. آنچه **رد** می‌کند که ساده باشد

| سنجه | نتیجه |
|---|---|
| همان فایل در انزوا، دو بار، همان DB | `pass 10 · fail 0` × ۲ |
| همان مسیرِ کد، سوئیتِ کاملِ پیشین (درختِ ادغام، DBِ تازه) | `1844 / 1844` |
| CIِ لینوکس روی `c92b1eb` | jobِ `test` **success** (219s) |
| سوئیتِ کاملِ **بعدی**، همان درخت، DBِ Postgresِ **تازه** (۰۳:۳۷–۰۴:۰۸ UTC) | `1844 / 1844 · EXIT=0` — `queue-lease-reclaim` سبز |
| jobهای باقی در DB پس از اجرا | فقط `push`ِ waitlist با `priority 3` — نمی‌توانند از `priority 1` جلو بزنند |
| jobِ `priority ≤ 1`ی باقی | **صفر** (hookهای `after` در پایانِ رانر پاک کردند — پس «۵۰ jobِ جلوتر» پس از واقعه دیدنی نیست) |

⚠️ **انزوا ردیه نیست** — همان خطایی که `UNPROVEN-otp-break-glass-ratelimit.md` §۱ ثبت کرده: انزوا بار و ترتیب را حذف می‌کند.

## ۳. مکانیزمی که می‌تواند این امضا را بسازد — در کد هست، علت‌بودنش اندازه‌گیری نشده

`api/src/lib/queue.ts`:

```ts
// enqueue — ساعتِ **Node**
runAfter: opts.runAfter ?? new Date(),
```
```sql
-- claimJobs — ساعتِ **Postgres**
WHERE status = 'pending' AND run_after <= now()
```

دو ساعت برای یک مقایسه. اگر ساعتِ کانتینرِ Postgres از ساعتِ میزبان عقب باشد (Docker Desktop روی ویندوز، به‌ویژه پس از
خوابِ ماشین)، jobی که همین حالا ساخته شد برای DB «در آینده» است و تا جبرانِ اختلاف claim نمی‌شود. متناوب بودن طبیعتِ آن است.

**اندازه‌گیری، پس از واقعه:** `clock_timestamp()`ِ DB منهای `Date.now()`ِ Node، پنج نمونه: `208 (rtt 472 — اتصالِ سرد)، -32، -22، 0، -2` ms.
یعنی **در لحظه‌ی اندازه‌گیری** اختلافی نبود. این نه تأیید است نه رد: اختلافِ لحظه‌ی واقعه ثبت نشده.

**چرا فقط تست نیست:** در تولید، API و DB روی دو میزبان‌اند. عقب‌بودنِ ساعتِ DB هر jobِ «فوری» را به همان اندازه عقب می‌اندازد
(پیامکِ تأییدِ رزرو، OTP نه — OTP همزمان است). احتمالاً ثانیه‌ها، نه دقیقه‌ها — ولی اندازه نگرفته‌ام.

`schema.prisma`: `runAfter DateTime @default(now())` — یعنی پیش‌فرضِ DB از قبل وجود دارد و `?? new Date()` آن را دور می‌زند.

## ۴. چرا رفعش نکردم

منشور §۳: «اگر نمی‌توانی بازتولیدش کنی، نفهمیده‌ای — UNKNOWN بنویس و برو.» حذفِ `?? new Date()` یک خط است و احتمالاً درست،
ولی **نمی‌توانم نشان دهم همان علتِ این پنج شکست است**. رفعی که روی علتِ فرضی بنشیند و بعدش سوئیت سبز شود، «رفع شد» را
بی‌شاهد ادعا می‌کند.

## ۵. راهِ قطعی‌کردن (ارزان)

1. پیش از `claimJobs` در تست، `SELECT now()` از DB و `new Date()` از Node را **هر دو** در پیامِ assert بیاور. شکستِ بعدی علت را با خودش می‌آورد.
2. یا تستی که `runAfter` را عمداً ۵۰۰ms جلوتر از `now()`ِ DB بسازد و claimِ فوری را بسنجد — قرمزش ثابت می‌کند مکانیزم وجود دارد (نه اینکه علتِ این واقعه بوده).
