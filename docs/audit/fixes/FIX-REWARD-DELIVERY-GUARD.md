## ۳. ریشه و کلاس

**ریشه:** `redeemRewardItem` یک زنجیره‌ی `if / else if` **بدونِ `else`** داشت. کیندی که هیچ شاخه‌ای
نمی‌گرفت، بی‌سروصدا از کنارِ تحویل رد می‌شد — ولی کسرِ سکه **بالاتر** از آن اتفاق افتاده بود و
هیچ‌چیز پرتاب نمی‌کرد، پس تراکنش commit می‌شد.

**کلاس:** «**آرتیفکت قابلیتی را ادعا می‌کند که مکانیزم ندارد**» — و مشخصاً: *فروختنی‌بودن* به‌جای
آنکه از **وجودِ مکانیزمِ تحویل** مشتق شود، یک ادعا در کامنت بود.

**دقیقاً همان کلاسی که این فایل قبلاً یک‌بار پرداختش کرده:** `coupon_grant`ِ بدونِ رستوران در
۲۰۲۶-۰۸-۲۰ (۵۰ سکه رفت، `result_coupon_id` = null، بدونِ خطا). تفاوت: آن یکی **داده‌ی خراب** بود و
این یکی **طراحیِ مستند**. مستند بودنِ یک رفتار آن را درست نمی‌کند.

## ۴. تغییر

**رجیستریِ تحویل** جایگزینِ زنجیره‌ی `if/else` شد (`rewards.ts`):

```ts
const DELIVERERS: Record<string, Deliverer> = { coupon_grant: …, gift_card_credit: … };
export const DELIVERABLE_KINDS = Object.freeze(Object.keys(DELIVERERS));
export function isDeliverableKind(kind: string) {
  return Object.prototype.hasOwnProperty.call(DELIVERERS, kind);
}
```

و در `redeemRewardItem`، **پیش از کسرِ موجودی و سکه**:

```ts
if (!isDeliverableKind(item.kind)) {
  throw Err.validation('این جایزه هنوز قابلِ دریافت نیست؛ سکه‌ای از شما کسر نشد');
}
```

بدنه‌ی هر دو تحویل‌دهنده **عیناً** منتقل شد؛ همه‌ی کامنت‌های زخمِ ۲۰۲۶-۰۸-۲۰ سرِ جایشان‌اند.

| فایل | تغییر |
|---|---|
| `api/src/lib/rewards.ts` | رجیستری + `isDeliverableKind` + گاردِ ردیم + `deliverable` در خروجیِ `listRewardItems` |
| `api/src/lib/incentive-engine.ts` | `deliverable` به تایپِ ورودی؛ فیلترِ `bestUnlocked`؛ نگاشت در `getIncentivesForUser` |
| `apps/customer/js/features/economy.js` | دکمه غیرفعال + برچسبِ «به‌زودی» وقتی `deliverable === false` |
| `standalone/customer.html` | همان تغییر در رونوشتِ دوم |
| `api/tests/reward-delivery-guard.integration.test.mts` | **جدید** — ۸ تست، در `_all.runner.mts` ثبت شد |
| `api/tests/rewards.integration.test.mts` | تستِ تبرک‌کننده **وارونه** شد؛ سه فیکسچر به کیندِ تحویل‌دار رفتند |
| `api/tests/incentive-engine.test.mts` | `deliverable: true` به فیکسچرها |

**هیچ فیچری حذف نشد.** آیتم‌ها همچنان در فهرست‌اند، فقط صادقانه علامت خورده‌اند — پس تصمیمِ

### ⚠️ قرمزِ اولِ من ضعیف بود، و قرمزِ دومم **از مسیرِ غلط سبز شد**

## ۶. جهش‌ها — سه تا، و **یکی گرفته نشد**

| جهش | چه چیزی خراب شد | نتیجه |
|---|---|---|
| **A** | گارد خنثی شد (`if (false && …)`) | ✅ **گرفته شد** — exit 1، ۳ fail |
| **B** | همان گارد، **منتقل‌شده به بعد از کسرِ سکه** | ❌ **گرفته نشد** — exit 0، ۸/۸ سبز |
| **C** | بازسازیِ نقصِ اصلی: کیندِ ناشناس بی‌صدا موفق شود (`?? (async () => NOTHING_DELIVERED)`) | ✅ **گرفته شد** — exit 1، ۳ fail، با پیامِ `Missing expected rejection` یعنی ردیم **موفق** شد |

هر سه پس از اندازه‌گیری برگردانده شدند (`grep -c "if (false)"` → `0`، `grep -c "?? (async"` → `0`).

### جهشِ B را چرا نمی‌پوشانم

چون یک **ادعای نادرستِ خودم** را رد کرد. در کامنتِ گارد نوشته بودم «اگر پایین‌تر بود، موجودی کم
می‌شد». **غلط است:** کلِ بدنه داخلِ `db.$transaction` است، پس هر throwی همه‌چیز را rollback می‌کند.
کامنت اصلاح شد و متنِ درست الان در کد است.

**نتیجه‌ی فنیِ مهم‌تر:** ضمانتِ واقعیِ پول **اتمیک‌بودنِ تراکنش** است، نه جایِ آن خط. آنچه گارد
*واقعاً* اضافه می‌کند، جهشِ C نشان می‌دهد: پیش از این هیچ خطایی پرتاب نمی‌شد و تراکنش **commit**
می‌شد. تستی که فقط جهشِ B را هدف بگیرد، ارزشی اثبات نمی‌کند — و من چنین تستی ننوشتم.

### ⚠️ یافته‌ی جانبیِ زیرساختی — برای CEO و هر کسی که DBِ تست می‌سازد

اولین ساختِ DBِ من با `prisma db push` بود و **۳ تست در `slot-lock-failopen-double-booking.test.mts`
قطعی می‌افتادند** (۲ اجرا از ۲، همان ۳ تست) — که شبیهِ فلیکِ شناخته‌شده‌ی CEO به نظر می‌رسید ولی
نبود. اندازه‌گیریِ مستقیم:

```text
DBِ من (db push):        reservations.id  column_default = (خالی)
DBِ مشترک (rezervno_test): reservations.id  column_default = gen_random_uuid()
0_init/migration.sql:154  "id" UUID NOT NULL DEFAULT gen_random_uuid()
```

`prisma db push` برای `@default(uuid())` **دیفالتِ سطحِ دیتابیس نمی‌سازد** (Prisma سمتِ کلاینت
تولید می‌کند). هر تستی که با `$executeRaw` و بدونِ `id` درج کند، روی چنین DBی با `23502` می‌افتد —
و `db push --accept-data-loss` دیفالت‌ها را حتی **حذف** می‌کند (اندازه‌گیری شد: پس از اجرا، خالی).

**درس:** «۳ تست افتاد» روی یک DBِ `db push`ی می‌تواند کاملاً آرتیفکتِ روشِ ساخت باشد، نه یافته.
DB بازساخته شد (initِ migration → push → بازگرداندنِ دیفالت روی ۵۴ جدول) و کلِ سوئیت دوباره اجرا شد.
