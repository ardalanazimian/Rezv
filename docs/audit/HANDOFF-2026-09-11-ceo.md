## پایانِ خط — آنچه سنجیده شد و آنچه هنوز نشده

نسخه‌ی اولِ همین بخش دو ادعای اثبات‌نشده داشت. Red Team به یکی‌شان با شاهدِ متضاد اعتراض کرد و حق داشت. این نسخه فقط چیزی را می‌گوید که اندازه گرفته شده.

**اندازه‌گیریِ ۱ — درختِ من «CRLF» نبود؛ ۳۸ فایل از ۱۳۸۴ بود.**

```
git ls-files --eol | uniq -c    →  1337  i/lf w/lf
                                     38  i/lf w/crlf      ← فقط این‌ها
```
پسوندها: ۱۵ `md` · ۹ `ts` · ۵ `mts` · ۲ `tsx` · ۲ `js` · ۲ `html` · ۱ `sql` · ۱ `mjs` · ۱ `json` — یعنی **فایل‌هایی که ابزار یا سشن‌ها نوشته‌اند**، نه خروجیِ checkout. `intelligence.js` یکی از همین ۳۸ است.

**اندازه‌گیریِ ۲ — روی این ۳۸ تا، `git status` واقعاً ساکت است، و علتش stat-cache نیست:**

```
git status --porcelain                    →  0 خط
git update-index --really-refresh; status →  0 خط   (پس stat-cache نبود)
git hash-object <فایلِ CRLFِ روی دیسک>     →  8c76a2c2fbe4
git rev-parse :<همان فایل>                →  8c76a2c2fbe4   ← برابر
```
git هنگامِ هش‌کردنِ فایلِ کاری، CR را حذف می‌کند؛ پس از دیدِ او تفاوتی وجود ندارد.

**اندازه‌گیریِ ۳ — و با این حال شاهدِ Red Team هم روی همین درخت بازتولید شد:**
یک فایلِ `w/lf` را به CRLF بردم و `git status` بی‌درنگ `M apps/company/js/analytics.js` داد. هر دو فایل `attr/text=auto eol=lf` دارند.

**آنچه سنجیده نشده: چرا این دو با هم فرق می‌کنند — و سه فرضیه که آزموده و رد شدند.**

| فرضیه | آزمون | نتیجه |
|---|---|---|
| نرمال‌سازیِ check-in روی فایلِ `M` اعمال نمی‌شود | `git hash-object` در برابرِ `git rev-parse :<path>` | **رد** — هر دو `bbeaabf69726`، یعنی فیلتر اعمال شد |
| محتوای فایل `text=auto` را از تشخیصِ «متن» می‌اندازد (``ِ تنها، BOM، بایتِ صفر) | شمارشِ بایت | **رد** — لونِ CR ۰، BOM ندارد، بایتِ صفر ندارد |
| stat-cache: اندازه عوض شده (۴۴۲۲ → ۴۵۰۶) پس git محتوا را دوباره نمی‌سنجد | `git update-index --really-refresh` سپس `status` | **رد** — `M` سرِ جایش ماند |

پس فایلی که هشِ فیلترشده‌اش **دقیقاً برابرِ بلابِ index** است باز هم `M` می‌گیرد، در حالی که ۳۸ فایلِ دیگر با همان وضع ساکت‌اند. **علت جدا نشده و کسی نباید رویش حساب کند.**

یک ردِ آزموده‌نشده که Red Team پیشنهاد داد و ارزشِ دنبال‌کردن دارد: اگر منشأِ آن ۳۸ تا واقعاً «نوشته‌شده توسطِ ابزار» باشد، باید در `git log` آخرین‌بار با کامیت‌های همین تیم عوض شده باشند. یک فایلِ CRLF بی‌صدا می‌ماند و دیگری `M` می‌گیرد، با همان attribute و همان تنظیمات. **علت جدا نشده است و کسی نباید رویش حساب کند.** ادعای نسخه‌ی اول که «`core.autocrlf=true` ریشه است» هم اثبات‌نشده بود: `.gitattributes` با `* text=auto eol=lf` حاکم است و طبقِ آن checkout باید LF بدهد — پس CRLFِ آن ۳۸ فایل از checkout نیامده، از **نوشته‌شدنشان** آمده. این با حدسِ Red Team («منشأِ CRLF، نه تنظیمات») می‌خواند، ولی حدس می‌ماند تا کسی اندازه‌اش بگیرد.

**قاعده‌ی عملی که هر دو رویش توافق داریم و به شاهد وابسته نیست:**
اسکنر بایتِ خام می‌خواند و `sink_hash` را از `expr + sourceLine` می‌سازد، پس CRLF هویتِ سینک را عوض می‌کند (`3af3d99dd758` با LF، `b41c49e82423` با CRLF). بنابراین **هر ادعایی درباره‌ی هشِ محتوا، شمارشِ بایت یا آرتیفکتِ تولیدشده باید روی checkoutِ تمیز گرفته شود، نه درختِ کاری** — چون روی این مخزن یک بار `M` دیده شد و یک بار هیچ هشداری نیامد، و ما نمی‌دانیم کدام حالت نصیبمان می‌شود.
