## ۰. یک‌خط

**یک باگِ واقعی روی مهم‌ترین عنصرِ صفحه، و بعد یک مسئله‌ی ساختاری.** روی موبایل، دو «درِ» انتخابِ
نقش — تصمیمِ خودِ مالک (D-006) برای اینکه مهمان **بدونِ خواندنِ چیزی** به اپ برسد — به دو قابِ
خالیِ ۴۲px له شده‌اند و متنشان بریده است. و بعد از آن: صفحه‌ی اول **۱۵٫۶ صفحه** اسکرول دارد، **۴ بومِ
متحرک**، و اسکرولش با **۳۰fps** می‌رود — نصفِ اپِ مشتری بعد از DS-008.

## ۱. L1 — درهای انتخابِ نقش روی موبایل بریده‌اند (⚠️ اولویتِ اول)

**دیده شد (`m-01-home.png`):** زیرِ «مهمانید یا صاحبِ رستوران؟» دو قابِ گردِ خالی، هر کدام فقط یک
شماره‌ی شبحِ «۰۱»/«۰۲» در گوشه. نه آیکون، نه «مهمانم، دنبالِ رزرو»، نه «صاحبِ رستورانم». روی دسکتاپ
(`d-01-home.png`) هر دو کامل‌اند.

**اندازه‌گیری (`getComputedStyle`، ۲۴۰۰ms بعد از بارگذاری، بعد از یک اسکرولِ ریز — پس reveal نیست):**

| | موبایل ۳۹۰ | دسکتاپ ۱۲۸۰ |
|---|---|---|
| `.doors` | `flex-direction: column`, ارتفاع **۱۰۰px** | `row`, ۳۵۲px |
| `.door` (جعبه) | **۴۲px** | ۳۵۲px |
| `.door.scrollHeight` (محتوا) | **۲۶۰px** | ۳۵۰px |
| `.door__title` | opacity ۱، display block، **۹۹px پایین‌تر از لبه‌ی بالای جعبه** | داخلِ جعبه |
| `.door overflow` | `hidden` | `hidden` |

متن هست، رنگ دارد، opacity ۱ — فقط **جعبه ۴۲px است و overflow:hidden بقیه را می‌بُرد.**

**مکانیزم (`apps/landing/app/site.css`):**

```css
.door { flex: 1 1 0; … overflow: hidden; … }            /* :1851 — basis صفر */
@media (max-width: 900px) {
  .doors { flex-direction: column; … }                    /* :2019 */
  .door, … { opacity: 1; flex-grow: 1; transform: none; } /* :2020-2022 */
}
```

در ردیف، `flex-basis:0` روی **عرض** عمل می‌کند و ارتفاع از محتوا می‌آید — درست. در **ستون**، محورِ
اصلی ارتفاع است: basis صفر + کانتینری که ارتفاعش auto است ⇒ هر در به کمینه‌اش می‌رسد، و
**کمینه‌ی خودکارِ آیتمِ flex با `overflow:hidden` صفر است** نه اندازه‌ی محتوا. می‌ماند پدینگ
(۲۰+۲۰) + بوردر ≈ **۴۲px**. دو در + gap ۱۶ = **۱۰۰px**. اعداد دقیقاً همین را می‌گویند.

**رفعِ پیشنهادی — یک خط در همان بلوکِ موبایل:** `.door { flex: 0 0 auto; }` (یا `flex-basis: auto`).
محتوا دوباره ارتفاع را تعیین می‌کند. **ابطال‌پذیری:** `door.getBoundingClientRect().height ≥
door.scrollHeight - 1` در ۳۹۰px — امروز ۴۲ در برابرِ ۲۶۰ → قرمز؛ بعد از رفع سبز. جهتِ دوم: دسکتاپ
باید ۳۵۲ بماند (رفع نباید ردیف را عوض کند).

**چرا اولویتِ اول:** این تنها مسیرِ **بی‌متنِ** مهمان به اپ روی موبایل است — همان چیزی که مالک
خواست — و روی موبایل **وجود دارد ولی دیده نمی‌شود**. منشور §۴h، بارِ چهارم.

## ۲. L2 — ساختار: صفحه‌ی اول یک داستانِ ۱۵صفحه‌ای است

| اندازه | موبایل | دسکتاپ |
|---|---|---|
| ارتفاعِ سند | ۱۳٬۱۵۹px = **۱۵٫۶ صفحه** | ۱۴٬۳۲۸px = ۱۷٫۹ صفحه |
| تعدادِ `<section>` | ۱۲ | ۱۲ |
| هیروِ «میزها پر، تلفن آرام» | از ۴۴۵px، **۱٬۳۵۶px بلند** (۱٫۶ صفحه برای یک هیرو) | ۱٬۵۵۵px |
| بخشِ pin (داستانِ چسبان) | — | **۳٬۶۸۰px** |
| `<canvas>` متحرک | **۴** | ۴ |
| `<img>` | ۰ | ۰ |

**خوانش از دیدِ ۲۲ساله:** این زبانِ **لندینگِ آژانسی** است — پرده، بومِ ذرات، داستانِ پین‌شده،
۱۲ بخش. اینستاگرام‌نسل ۱۵ صفحه نمی‌خواند؛ **در دو ثانیه‌ی اول تصمیم می‌گیرد.** و آن دو ثانیه امروز:
پرده‌ی ۱٫۲ ثانیه‌ای (§۳) + درهای بریده (§۱) + هیرویی که به **صاحبِ رستوران** حرف می‌زند (§۶).

**چه چیزی خوب است و نباید قربانی شود:** ترتیبِ «اول در، بعد هیرو» (D-006) درست است؛ Vazirmatn
self-hosted و RTL منطقی رعایت شده (baseline)؛ نوارِ بالا روی موبایل به یک CTA («رزرو میز») و منو
جمع شده.

## ۳. L3 — فریم‌تایم: لندینگ ۳۰fps است، اپ ۶۰

همان ابزار و پروتکلِ اپ (`tools/measure-scroll-frametime.mjs 3 http://localhost:3200/`):

| | p50 | p95 (median) | >33ms | worst |
|---|---|---|---|---|
| لندینگ، صفحه‌ی اول | **۳۳٫۳** | ۵۰ | **~۸۵٪** | ۸۳ |
| اپِ مشتری بعد از DS-008 | ۱۶٫۷ | ۱۶٫۸ | ~۲٪ | ۳۳ |

**p50 = 33ms یعنی فریمِ میانه دو برابرِ بودجه است**، نه فقط دُمِ توزیع. مظنونِ اصلی: ۴ بومِ `rAF`
(FlowField/Caustics/LiveFlow — کد می‌گوید `IntersectionObserver` و `reduced-motion` را رعایت
می‌کنند، **نسنجیدم**) + بخشِ pin. **علت جدا نشد**؛ برای اثبات باید بوم‌ها را یکی‌یکی خاموش کرد و
دوباره سنجید. قیدِ همیشگی: headless روی PC — ولی ۳۰fps روی PC، روی گوشیِ میان‌رده بدتر می‌شود، نه بهتر.

## ۴. L4 — پرده‌ی ورود (Intro)

۱٫۲ ثانیه، تمام‌صفحه، فقط بارِ اول در هر نشست، با reduced-motion اصلاً رندر نمی‌شود، بی‌JS هم بالا
می‌رود (`Intro.tsx` — خوب ساخته شده). **ولی خودِ کامنتِ کد می‌گوید «روی LCP می‌نشیند».** برای ۲۲ساله‌ای
که از یک لینک آمده، ۱٫۲ ثانیه «رزرونو … ۲۴» پیش از هر محتوا **قیمتِ اولین برداشت** است. این نقص
نیست؛ **تصمیمِ محصولی** است — مالک باید بگوید پرده می‌ماند یا نه. پیشنهادِ من: نه، یا فقط ۴۰۰ms.

## ۵. L5 — `/customer-app`: CTA ِ اصلی برای صاحبِ رستوران است

**دیده شد (`m-10-customer-app.png`):** روی صفحه‌ی **اپِ مشتری**، دکمه‌ی پررنگِ اصلی «**من رستوران
دارم** ←» است و «دیدنِ رستوران‌ها» دکمه‌ی ثانویه‌ی توخالی. **مخاطب وارونه است.**

**محل:** در **مخزن نیست.** `app/customer-app/page.tsx` فقط `<CmsPage slug="customer-app">` است و رشته‌ی
«من رستوران دارم» در هیچ فایلِ کد پیدا نمی‌شود — **محتوای CMS/استودیو** است. همان سوراخِ ایستاده‌ای
که منشور نام برده: هیچ ممیزیِ مخزنی نمی‌تواند این را بگیرد یا ببندد. **رفع در استودیو است**، و
پیشنهادِ گارد: یک قاعده‌ی محتوایی که «CTA ِ اصلیِ صفحه‌ی مشتری باید به `appBase()` برود» — ولی
گاردِ محتوای CMS خارج از دامنه‌ی این سند است.

## ۶. L6 — هیروِ صفحه‌ی اول به صاحبِ رستوران حرف می‌زند

بلافاصله زیرِ درها: «**میزها پر، تلفن آرام.** رزرونو رزروِ آنلاینِ مهمان را به پنلِ عملیاتیِ رستورانِ
شما وصل می‌کند…». وقتی درها می‌گویند «هر دو طرفِ میز»، اولین پیامِ واقعیِ صفحه فقط برای یک طرف است.
مهمانی که هنوز دری را نزده، B2B می‌خواند. **تصمیمِ کپی/محصول** — یا هیروِ دوصدایی، یا هیرو **بعد از**
انتخابِ در (که عملاً یعنی صفحه‌ی اول همان درهاست و بس — مینیمالِ واقعی).

## ۸. آنچه این سند نمی‌گوید

- **هیچ تغییری در لندینگ اعمال نشد.** `apps/landing/**` لِینِ من نیست؛ سرورش فقط برای اسکرین‌شات
  از checkout ِ اصلی اجرا شد.
- علتِ ۳۰fps جدا نشد (بوم‌ها vs pin vs بقیه). «مظنون» است، نه یافته.
- «۲۲ساله در دو ثانیه تصمیم می‌گیرد» ادعای عمومی است؛ خطِ مبنای بیرونی نداریم.
- reduced-motion ِ بوم‌ها از **کد** خوانده شد (هر سه کامپوننت ارجاع دارند)، **در مرورگر سنجیده نشد.**
- L5 از یک بارِ رندرِ CMS آمده؛ اگر استودیو محتوا را عوض کند، این ردیف بی‌اعتبار می‌شود — به همین
  دلیل تاریخ‌دار است.
