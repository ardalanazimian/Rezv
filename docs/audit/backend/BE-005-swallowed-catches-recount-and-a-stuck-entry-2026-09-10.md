## ۱. عدد: ۹۲ در ۴۲ فایل — و **نمی‌گویم ۰۴۴ اشتباه شمرده**

با AST خودِ TypeScript شمرده شد، نه grep: `api/tools/count-swallowed-catches.mjs`
(در همین تحویل). خروجی روی HEAD:

```text

کلِ catchها: ۲۳۴ بلوکِ catch + ۹۱ فراخوانِ .catch()

```

**⚠️ این «۷۱ غلط بود» نیست، و مقایسه‌ی مستقیمشان صادقانه نیست.** تعریفِ من
عمداً گشادتر است: علاوه بر بدنه‌ی خالی، `.catch(() => [])`، `=> null`،
`=> 0`، `=> ''`، `=> false` و `=> ({})` را هم می‌شمارد — یعنی هر handlerی که
خطا را دور می‌ریزد و یک لیترالِ بی‌خطر برمی‌گرداند. ۰۴۴ ممکن است فقط بدنه‌ی
خالی را شمرده باشد.

**آنچه می‌شود گفت:** عدد با یک تعریفِ نوشته‌شده و یک ابزارِ قابلِ‌اجرا دوباره
گرفته شد، و از این به بعد هر کس می‌تواند با آن اختلاف کند. ابزار خودش هم
falsifiable است: فهرستِ اسکنِ خالی ⇦ کدِ ۲؛ صفر catch از هر نوعی ⇦ کدِ ۲.
هیچ‌وقت «۰ بلعنده» به‌دلیلِ ابزارِ خراب چاپ نمی‌کند.

## ۳. و یک قاعده که در حین کار روشن شد و از خودِ شمارش مفیدتر است

قاعده‌ی ۰۴۴ («پول، رکورد، یا پیام») **کافی نیست** — با آن، `fraud.ts:302`
بلعنده‌ی بدی به نظر می‌رسد (تشخیصِ تقلب شکست می‌خورد ⇒ کسی فلگ نمی‌شود ⇒ پول).
من خودم در `BE-002 §۳` همین را علامت زدم. **ولی ۰۴۴ `fraud.ts` را در دسته‌ی
«وقت نگذار» گذاشته، و حق با ۰۴۴ است.**

تفاوت را این سؤال می‌سازد:

> **آیا شکستِ بلعیده‌شده داده را از دست می‌دهد، یا فقط یک محاسبه‌ی مشتق را
> عقب می‌اندازد؟**

`detectReferralFarming` سیگنال‌ها را از داده‌ی ذخیره‌شده مشتق می‌کند و
`customer-insights` هر روز ساعتِ ۳ دوباره می‌دود (`cron/crontab:30`). یک اجرای
شکست‌خورده **چیزی را از دست نمی‌دهد** — اجرای بعدی همان را دوباره می‌سازد.

**پس علامتِ من روی `fraud.ts:302` را پس می‌گیرم.** با قاعده‌ی «پول/رکورد/پیام»
درست به نظر می‌رسید و با قاعده‌ی بازیابی‌پذیری غلط است. قاعده‌ی دقیق‌تر این
است:

> بلعیدن وقتی درست است که شکست **بازیابی‌پذیر** باشد — یعنی یک اجرای بعدی،
> بدونِ دخالتِ انسان، همان نتیجه را دوباره بسازد. وقتی غلط است که شکست
> **جبران‌ناپذیر** باشد یا سیستم را در حالتی بگذارد که هیچ اجرای بعدی
> نمی‌بیندش.

نیمه‌ی دومِ همین جمله، §۴ را پیدا کرد.

## ۴. یافته‌ی واقعی — `waitlist.ts:718`، و کامنتش در همان حالتی که بلعیدن می‌سازد باطل است

```ts
// api/src/lib/waitlist.ts:710-720
} catch (err) {
  // بازگردانی به *دقیقاً* حالتِ قبل: ورودی دوباره `offered` و میز `reserved`
  // می‌ماند … اگر ساختِ رزرو مدام شکست بخورد، آفر تا پایانِ TTL می‌ماند و
  // بعد cron خودش تمیزش می‌کند.
  await db.waitlistEntry.updateMany({
    where: { id: entryId, status: 'accepted' },
    data: { status: 'offered', respondedAt: null, seatedAt: null },
  }).catch(() => {});
  throw err;
}
```

این یک **نوشتنِ جبرانی** است و بلعیده می‌شود. کامنت استدلال می‌کند که بازیابی
هست: «cron تمیزش می‌کند». **آن استدلال فرض می‌کند جبران موفق شده.**

```ts
// api/src/lib/waitlist.ts:839-841
export async function expireOffers(): Promise<ExpirySweepResult> {
  … where: { status: 'offered', offerExpiresAt: { lt: new Date() } }
```

**جارو فقط `offered` را می‌بیند.** اگر جبران شکست بخورد، ورودی روی `accepted`
می‌ماند — دقیقاً همان وضعیتی که `expireOffers` هرگز لمسش نمی‌کند.

**پیامد، در همان حالتی که بلعیدن می‌سازد:**

- ورودی برای همیشه `accepted` است، با `reservationCode` خالی (چون
  `createReservation` throw کرد).
- میز عمداً `reserved` می‌ماند — کامنتِ بالاترش می‌گوید آزادکردنش نشتِ دیگری
  می‌ساخت، و درست هم می‌گوید. **ولی حالا هیچ‌چیز آزادش نمی‌کند.**
- مهمان «پذیرفته‌شده» می‌بیند بدونِ کدِ رزرو.
- **هیچ اجرای بعدی این را نمی‌بیند.** جبران‌ناپذیر، به‌حکمِ where-clause.

**احتمالش کم است** و صریح می‌گویمش: دو شکستِ پشتِ‌هم لازم است —
`createReservation` و بعد خودِ جبران. ولی این دقیقاً شکلِ همان مسیرهای مرکبی
است که `P2028` و `P2024` در همین مخزن از آن‌ها بیرون آمدند، و آن دو هم ماه‌ها
«flake» خوانده می‌شدند.

**⚠️ آنچه اثبات نکرده‌ام:** این را با یک تستِ واقعی بازتولید **نکردم**. از
خواندنِ دو where-clause و مقایسه‌شان درآمد. تا وقتی بازتولید نشده، «یک نقصِ
استدلالی» است نه «یک باگِ اندازه‌گیری‌شده» — و منشور می‌گوید کدامش را کردم
بگویم.

## ۵. رفعِ پیشنهادی — و چرا خودسرانه نزدمش

دو نیمه، و نیمه‌ی دوم است که سوراخ را می‌بندد:

1. **شکست را دیدنی کن.** `.catch(() => {})` جای خودش را به یک `log.error` بدهد
   که `entryId` را می‌برد. ارزان، بی‌ریسک. **به‌تنهایی تقریباً بی‌فایده است** —
   لاگی که کسی نمی‌خواند.
2. **مسیرِ بازیابی‌ای که کامنت ادعایش را می‌کند واقعاً بساز:** `expireOffers`
   ورودی‌های یتیم را هم جارو کند — `status: 'accepted'` و
   `offerExpiresAt < now` و `reservationCode: null`. آن‌وقت کامنت راست می‌شود.

**نزدمش چون:** `expireOffers` همان تابعی است که خودِ این فایل «پرریسک‌ترین
تغییرِ آن دور» صدایش می‌زند، شرطِ claimِ داخلِ تراکنشش
(`:872 where: { id, status: 'offered' }`) هم باید همراهش گشاد شود، و جهش‌آزماییِ
قبلی نشان داده بود که حذفِ شرطِ انقضا هیچ تستی را قرمز نمی‌کند. یعنی این جایی
است که یک تغییرِ به‌ظاهر ساده می‌تواند بی‌صدا رد شود.

**می‌خواهم:** یا حکم بده بزنمش (با تستِ بازتولید **اول**، بعد رفع، و چرخه‌ی
قرمز→سبز مثلِ `ef2df7b`)، یا اول بازبین این تحلیل را ببیند. هر کدام را بگویی
همان را می‌کنم. **خودم `A1-005`وار بازش نمی‌گذارم و خودسرانه هم نمی‌بندمش.**
