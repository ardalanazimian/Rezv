## خلاصه‌ی اجرایی

منشورِ من (`docs/audit/prompts/backend-engineer.md` §۲ و §۶‑۱) می‌گوید بالاترین کاری که
می‌توانم باز کنم `E-002` است، که «روی دقیقاً یک عدد قفل است: چند امتیاز در **production**
معوق است»، و مرا برای گرفتنش به **Supabase** ارجاع می‌دهد.

**هر دو نیمه‌ی این دستور با منبع نمی‌خوانَد، و اندازه‌گیری کردم — نقل نکردم:**

| ادعای منشور | آنچه اندازه‌گیری شد |
|---|---|
| «Supabase مهم‌ترین ابزار برای توست، یک پروژه‌ی production زنده هست» | Supabase اصلاً production نیست (§۱)، و data-plane هم جواب نمی‌دهد: `28P01`، دو بار (§۲) |
| «`E-002` روی یک کوئریِ read-only قفل است» | `E-002` **به‌خواستِ صریحِ خودِ مالک پارک است**، و چیزی که کم دارد یک **تصمیم** است نه یک اندازه‌گیری (§۴) |

**و عددِ درست هم از مسیرِ دوم درنمی‌آید:** استکِ production روی این دستگاه اصلاً بالا نیامده
و هیچ‌وقت نیامده (§۳).

**پس جوابِ صادقانه به «چند امتیاز معوق است؟» امروز `UNKNOWN` است — نه صفر، نه «تقریباً هیچ».**
این دقیقاً همان تمایزی است که منشور سه بار در یک هفته بابتش هزینه داده.

## ۱. Supabase پایگاهِ production نیست — و این ادعای من نیست، ادعای خودِ مخزن است

منشورِ ممیزی (`.claude/skills/rezervno-audit-constitution/SKILL.md` §۶) صریح است:

> **Production database = Postgres inside the Docker stack** (founder decision, P0-014,
> 2026-09-03). Supabase is off the critical path and awaits decommission.

دو اندازه‌گیریِ مستقل که همین را می‌گویند:

```text
$ grep -rln "supabase" api/src | wc -l
0                                   ← کلِ سورسِ اپلیکیشن، صفر ارجاع

$ grep -n DATABASE_URL docker-compose.yml
58:  DATABASE_URL: postgresql://${POSTGRES_USER:-rezervno}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB:-rezervno}
                                                                              ↑ سرویسِ compose، نه Supabase
```

یعنی حتی اگر آن پروژه پاسخ می‌داد، عددی که می‌داد **عددِ production نبود** — عددِ یک پایگاهِ
در انتظارِ decommission بود. این بدترین حالتِ ممکن است: یک عددِ باورپذیر که به سؤالِ دیگری
جواب می‌دهد.

## ۲. و پاسخ هم نمی‌دهد — `ACTIVE_HEALTHY` دوباره غلط از آب درآمد

منشورِ من خودش هشدارش را نوشته بود («`ACTIVE_HEALTHY` یک فیلدِ **cached** است، با یک کوئریِ
واقعی cross-check کن»). کردم:

```text
control-plane:
  mcp Supabase list_projects
  → { name: "rezervno", id: "zmyuvtpbchytqvtgyewt", status: "ACTIVE_HEALTHY", region: eu-central-1 }

data-plane (همان پروژه، دو بار):
  execute_sql  select current_database(), now(), count(tables)
  → FATAL: 28P01: password authentication failed for user "postgres"
  execute_sql  select 1 as probe
  → FATAL: 28P01: password authentication failed for user "postgres"
```

**و این خطا از قبل پیش‌بینی شده بود.** `audit/round-19/supabase-decommission-checklist.md`،
بخشِ «Live-query note»:

> While the project is paused, **no** row count can be obtained — `execute_sql` returns `28P01`,
> which on 2026-09-03 was misread as a credential fault and is in fact the pause presenting itself.

پس `28P01` را **به‌عنوان نقصِ اعتبارنامه گزارش نمی‌کنم**؛ همان اشتباهی است که P0-014 بابتش
تصحیح خورد. خواندنِ درست: پروژه paused است و D1 چک‌لیست هنوز انجام نشده.

## ۳. مسیرِ دوم هم بسته است — استکِ production روی این دستگاه هرگز اجرا نشده

اگر production همان Postgresِ داخلِ Docker است، عدد باید آنجا باشد. نیست:

```text
$ docker version --format '{{.Server.Version}}'      → 29.7.2        (EXIT=0، خودِ ابزار سالم است)

$ docker ps -a --format '{{.Names}}|{{.Image}}|{{.Status}}'
rezv-test-redis|redis:7-alpine|Up 2 hours
rezv-test-pg|postgres:16-alpine|Up 2 hours
                                                    ← فقط دو کانتینرِ تست. حتی متوقف‌شده هم چیزی نیست.

سرویس‌هایی که docker-compose.yml تعریف می‌کند و هیچ‌کدام وجود ندارند:
  postgres · redis · api · nginx · backup · cron

$ docker volume ls --format '{{.Name}}' | grep -iE "pgdata|rezervno"
(خروجی خالی)  EXIT=1                                ← والیومِ داده‌ی production ساخته نشده

$ ls .env api/.env
(هیچ‌کدام نیست؛ فقط .env.example)
docker-compose.yml:17  POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?...}
                                            ↑ اجباری. بدونِ .env استک اصلاً بالا نمی‌آید.
```

**آنچه این ثابت می‌کند:** روی این دستگاه پایگاهِ production وجود ندارد و هرگز اجرا نشده.
**آنچه ثابت نمی‌کند:** اینکه production جایی وجود ندارد. ممکن است روی سروری باشد که من
نمی‌بینم. **آن `UNKNOWN` است و همان‌طور ثبت می‌شود** — «پیدا نکردم» شاهدِ نبودن نیست.

### یک عارضه‌ی جانبی: سؤالِ بازِ خودِ `E-002` هم همین‌جا جواب می‌گیرد

`E-002` این را باز گذاشته بود:

> «آیا کانتینرِ `cron` در محیطِ واقعیِ مالک در حال اجراست؟ این یک واقعیتِ استقرار است، نه مخزن.»

**روی این دستگاه: نه، اجرا نمی‌شود** (بالا، `docker ps -a`). روی محیطِ دیگری: `UNKNOWN`.
این نیمه‌ی سؤال را می‌بندد، نه کلش را. و مهم است، چون کلِ استدلالِ «پنجره‌دار بودنِ ریسکِ
رزروِ جعلی» به شلیکِ واقعیِ همان cron وابسته است.

## ۴. و اصلاً `E-002` روی یک عدد قفل نیست

منشورم می‌گوید «تصمیمِ اقتصادِ امتیاز با مالک است، ولی تصمیم به عددی نیاز دارد که کسی
تولیدش نکرده». `audit/ESCALATIONS.md` چیزِ دیگری می‌گوید:

- **وضع:** «**پارک، به‌خواستِ صریحِ مالک**» — با نقلِ مستقیم: «cant find the answer for this
  right now… lets do other things for now».
- چیزی که واقعاً کم است یک **تصمیم** است نه یک اندازه‌گیری: سه گزاره‌ی مالک درباره‌ی نرخ
  (۱ امتیاز = ۲ تومان · ۱۰۰۰ تومان خرج = ۲۵ امتیاز · ۲۰۰ امتیاز = ۱۰۰۰۰ تومان) **با هم
  ۱۲۵٪ کش‌بک می‌دهند** و نمی‌توانند هم‌زمان درست باشند.
- و کوئری‌های شمارشِ موجودی **از قبل نوشته شده‌اند** — در پیامِ تحویلِ کامیتِ `c15362c`.
  چیزی که نیست، پایگاهی است که رویش اجرا شوند.

پس ترتیبِ درست وارونه‌ی چیزی است که منشور می‌گوید: **عدد تصمیم را باز نمی‌کند؛ تصمیم است
که عدد را معنادار می‌کند.** ضمناً `points_redemption_enabled` در `DEFAULT_OFF` است
(`api/src/lib/feature-flags.ts:75`) — امروز هیچ امتیازی خرج‌شدنی نیست، پس تأخیر ریالی
هزینه ندارد؛ فقط دفتر با نرخِ ۲ تومان پر می‌شود.

## ۵. توصیه — و تنها چیزی که از مالک می‌خواهم یک جمله است

1. **دنبالِ عددِ Supabase نروید، و §۲ منشورِ من اصلاح شود.** هزینه‌ی نرفتن صفر است؛ هزینه‌ی
   رفتن یک عددِ باورپذیرِ غلط است که وارد دفتر می‌شود.
2. **سؤالِ مالک (برگشت‌پذیر، یک جمله):** «production امروز کجا اجرا می‌شود؟» سه حالت:
   - **جایی مستقر است** → مسیرِ دسترسیِ read-only را بدهید، عدد را همان‌روز می‌گیرم.
   - **هنوز مستقر نشده** → آنگاه «امتیازِ معوق در production» سؤالِ **بی‌موضوع** است و باید
     از `E-002` حذف شود، نه اینکه باز بماند و شبیهِ کارِ انجام‌نشده به نظر برسد.
   - **مطمئن نیستید** → همان `UNKNOWN` ثبت می‌شود، که وضعِ فعلیِ درست است.
3. **تا آن جمله، من روی چیزهایی کار می‌کنم که به هیچ تصمیمی وابسته نیستند** — هر دو در
   §۶ منشور و هر دو مستقل از نرخ:
   - `A1-005`: `completeReferral` صفر صداکننده دارد در حالی که پنلِ مشتری «۵۰۰ امتیاز برای
     هر دعوت موفق» را وعده می‌دهد. **وعده‌ای که کد بلد نیست انجام دهد تقلبِ کاربر نیست، مالِ
     ماست.** سیم‌کشی‌اش پول خرج می‌کند و مالِ مالک است؛ **گفتنش نه.**
   - `CHECK (points >= 0)` روی `club_members.points` که در `schema.prisma` نیست و
     `points_ledger` هم ندارد — و `check-schema-drift` به‌حکمِ ساختار نمی‌تواند ببیندش،
     چون Prisma اصلاً `CHECK` را بیان نمی‌کند. این همان الگوی §۴c است: گارد فهرستش را از
     جایی می‌گیرد که خطر آنجا نیست.

## ۶. اندازه‌گیریِ ظرفیتِ این نشست — با control، چون منشور همین را می‌خواهد

منشور می‌گوید «نتیجه‌ی منفی‌ای که controlش هم منفی است، ابزارِ خرابِ توست نه غیابِ موضوع».
پس control اول:

| ابزار | نقش | نتیجه |
|---|---|---|
| `mcp Context7 resolve-library-id` | **control** — یک MCP سرورِ دیگر | ✅ پاسخِ کامل. یعنی transportِ MCP در این نشست زنده است |
| `mcp Supabase list_projects` | control-plane | ✅ سه پروژه برگشت |
| `mcp Supabase execute_sql` | **subject** — data-plane | ❌ `28P01` ×۲ |
| `docker` | — | ✅ سرور 29.7.2، `ps -a` و `volume ls` هر دو با کدِ خروجِ ۰ |
| `git` / worktree | — | ✅ `wt-rezv-89` ساخته شد، `node_modules` هر سه اپ junction شد |

**نتیجه‌گیریِ مجاز:** `28P01` یک واقعیت درباره‌ی **آن پروژه** است، نه درباره‌ی نشستِ من —
چون هم control سبز است و هم control-planeِ همان سرور. اگر Context7 هم مرده بود، هیچ چیزی
درباره‌ی Supabase یاد نگرفته بودم.

## ۷. خطای خودم، پیش از آنکه کسی پیدایش کند

اولین کاوشِ من روی `rezv-test-pg` این بود:

```text
docker exec rezv-test-pg psql ... 2>&1 | head -5 ; echo "EXIT=$?"
→ EXIT=0        ← دروغ. psql شکست خورده بود؛ ۰ مالِ `head` بود.
```

**عیناً همان تله‌ای که منشور §۳ نام می‌بردش: «`EXIT=$?` بعد از pipe کدِ آخرین مرحله را
می‌خواند».** با گرفتنِ خروجی در متغیر و خواندنِ کد **پیش از هر pipe** دوباره زدم:

```text
out=$(docker exec rezv-test-pg psql -U rezervno -d rezervno -tAc "…" 2>&1); ec=$?
→ EXIT=2   OUT=FATAL: database "rezervno" does not exist
```

هیچ نتیجه‌ای از خواندنِ اول در این سند نیامده. ثبتش می‌کنم چون منشور می‌گوید اشتباهی که
خودت رو کنی یک پاراگراف خرج دارد و همان اشتباه اگر بعداً پیدا شود اعتبارِ هر ادعای دیگری
را می‌برد. **و ضمناً `rezv-test-pg` پایگاهِ `rezervno` را ندارد** — یعنی حتی به‌عنوان
منبعِ عدد هم مطرح نیست.
