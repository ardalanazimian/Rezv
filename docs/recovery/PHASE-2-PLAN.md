## ۱. خلاصه‌ی اجرایی — تصویرِ واقعیِ سلامتِ سیستم

پس از تأییدِ مستقلِ کد، تصویر **دوقطبی** است و این مهم‌ترین نکته‌ی این سند است:

**لایه‌ی بک‌اندِ هسته‌ای، به‌طورِ غیرمنتظره‌ای سالم است.**
state machine واقعاً متمرکز است، double-booking در سطحِ **دیتابیس** (EXCLUDE
constraintِ GiST) مهار شده نه در فرانت، تله‌متری فیلدهایِ حساس را server-authoritative
می‌کند، دفترِ امتیاز append-only است، و ۵۱۰/۵۱۰ تست سبز است.

**شکافِ واقعی در سه جایِ مشخص است:**
1. **مرزِ شعبه** — یک fallbackِ خاموش که نوشتن را به شعبه‌ی اشتباه می‌برد (P0-1)
2. **یک endpointِ جهشی بدونِ احراز هویت** (P0-2)
3. **لایه‌ی فرانت که در قطعیِ شبکه، حقیقتِ کسب‌وکار را جعل می‌کند** (P0-3، P0-4)

یعنی: **کارِ فازِ ۲ جراحیِ دقیق است، نه بازسازی.** این با §۳۲ کاملاً هم‌راستاست.

## ۳. تأییدِ آنچه **قبلاً درست است** (و نباید دست بخورد)

طبقِ §۳۲ و §۲۲ («reuse before abstraction»)، ثبتِ آنچه سالم است به‌اندازه‌ی
ثبتِ آنچه شکسته است اهمیت دارد — چون از «رفعِ» چیزِ سالم جلوگیری می‌کند.

### ۳.۱ چرخه‌ی حیاتِ رزرو — **canonical است** (§۴ عمدتاً برآورده)

`api/src/lib/lifecycle.ts` تنها نویسنده‌ی مجازِ `reservation.status` است:

- جدولِ `TRANSITIONS` کاملِ state machine (۱۸ وضعیت) — انتقالِ نامعتبر `Err.invalidTransition`
- هر انتقال اتمیک در `db.$transaction`: به‌روزرسانی + `reservationEvent` (audit) با هم
- `processReservationEconomyEvent` و `enqueueSms` بعد از commit، با catch — اعلان هرگز تراکنش را نمی‌شکند
- باطل‌سازیِ کشِ availability با **تاریخِ محلیِ رستوران**، نه UTC

مصرف‌کننده‌هایِ تأییدشده که همگی از همین مسیر رد می‌شوند:
`markArrival` (`reservations.ts:719`) · `expireStaleHolds` و `markLateNoShows`
(`reservation-lifecycle-ops.ts`) · `qrCheckIn` (`tables.ts:103`) ·
`autoMarkRunningLate` / `autoMarkNoShow` / `autoComplete` (`lifecycle.ts`).

grepِ `db.reservation.update` تنها ۵ نتیجه داد — **هیچ‌کدام `status` را نمی‌نویسند**
(چهارتا `depositStatus`، یکی `cancelReason`). grepِ SQLِ خام برایِ `SET status` هم
فقط `idempotency.ts` و `queue.ts` (جدول‌هایِ دیگر) را برگرداند.

> **اقدام: هیچ بازنویسی‌ای انجام نمی‌شود.** فقط تستِ رگرسیون اضافه می‌شود که این
> انحصار را **پین** کند (Batch 5)، تا آینده به‌سادگی نشکندش.

### ۳.۲ مرجعِ availability — **تعریف‌شده و درست است** (§۵ برآورده)

سه لایه واقعاً از هم جدا هستند:

| لایه | فایل | نقش |
|---|---|---|
| نمایش (fallback) | `apps/customer/js/data/booking.js:65-93` | سانسِ نمونه وقتی slug/شبکه نیست |
| کشِ خوانشی | `availability.ts` + `availability-cache.ts` | SWR: ۳۰s تازه، تا ۳۰۰s stale |
| **مرجعِ واقعیِ رزرو** | `prisma/sql/026-consolidate-exclusion-constraint.sql` | `EXCLUDE USING gist` رویِ `(table_id, tsrange(slot_start, block_end))` |

نکته‌ی کلیدی: مرجع در **دیتابیس** است، نه در کش و نه در فرانت. یعنی الزامِ صریحِ
پروتکل — «A fallback may help UX. It must NEVER authorize a real reservation» و
«Backend/database must enforce the invariant» — **از قبل برآورده است**.
دو رزروِ هم‌زمان رویِ یک میز حتی اگر هر دو کشِ stale ببینند، در سطحِ Postgres رد می‌شود.

### P0-1 · نشتِ خاموشِ شعبه در `resolveStaffRestaurant`

- **فایل:** `api/src/lib/staff-helpers.ts:68-79`
- **دامنه:** Tenant/Branch Isolation · **بخشِ ۷**
- **شدت: بحرانی (یکپارچگیِ داده).**

**شواهد — کد خودش این رفتار را اعتراف می‌کند:**

```ts
const requestedId = req?.headers.get('x-restaurant-id');
if (requestedId) {
  const restaurant = await db.restaurant.findFirst({
    where: { id: requestedId, tenantId: auth.tenantId },
    select: RESTAURANT_SELECT,
  });
  if (restaurant) return restaurant;
  // هدر نامعتبر/متعلق به تنانتِ دیگر → به fallback زیر می‌افتیم به‌جای خطا،
  // چون این می‌تواند یک شعبه‌ی حذف‌شده یا انتخابِ قدیمیِ کلاینت باشد.
}
const restaurant = await defaultRestaurantForTenant(auth.tenantId); // ← قدیمی‌ترین شعبه
```

**ریشه‌ی مشکل:** یک تصمیمِ «مهربانی با UX» که به الزامِ صریحِ پروتکل تبدیل به نقض شده.
پروتکل §۷: *«If a specific branch is requested: invalid branch / inaccessible branch /
deleted branch must produce an explicit error. Never silently use another branch.»*

**چرا بحرانی است — این فقط خواندن نیست:** `resolveStaffRestaurant` از داخلِ
`withRestaurantAuth` صدا زده می‌شود، یعنی `ctx.restaurant.id` که به **همه‌ی**
handlerهایِ restaurant-scoped می‌رود — شاملِ **نوشتن‌ها**. سناریویِ واقعی:
مالکِ دو شعبه‌ای، شعبه‌ی B را در پنل انتخاب کرده؛ B حذف/غیرفعال می‌شود یا هدر کهنه
می‌ماند → **واک‌این، رزروِ دستی، تغییرِ وضعیتِ میز، کمپینِ مارکتینگ و شارژِ SMSِ او
بی‌صدا رویِ شعبه‌ی A ثبت می‌شود** و پنل هم داده‌ی A را نشانش می‌دهد. هیچ خطا،
هیچ نشانه‌ای. این دقیقاً همان کلاسِ باگی است که کامنتِ `defaultRestaurantForTenant`
می‌گوید قبلاً یک‌بار در همین فایل رخ داده بود.

**رفعِ پیشنهادی:** وقتی هدرِ `X-Restaurant-Id` **صریحاً داده شده** ولی resolve نمی‌شود
→ خطایِ صریحِ ساختاریافته (`404` با کدِ `BRANCH_NOT_ACCESSIBLE`)، نه fallback.
مسیرِ بدونِ هدر (تنانتِ تک‌شعبه‌ای) دست‌نخورده می‌ماند تا سازگاری نشکند.

**ریسک:** پنلِ business با `restaurantId`ِ کهنه در localStorage، به‌جایِ داده‌ی شعبه‌ی
اشتباه، خطا می‌گیرد. **این خودِ رفع است، نه عارضه** — ولی فرانت باید این ۴۰۴ را
تمیز مدیریت کند (پاک‌کردنِ انتخابِ کهنه + سوییچ به شعبه‌ی پیش‌فرض با اطلاعِ کاربر).

**وابستگی:** رفعِ فرانت باید **هم‌زمان** با بک‌اند برود، وگرنه پنل قفل می‌شود.

**استراتژیِ تست:** تستِ یکپارچگیِ منفی — (الف) هدرِ شعبه‌ی تنانتِ دیگر → ۴۰۴،
نه داده‌ی شعبه‌ی خودی؛ (ب) هدرِ UUIDِ ناموجود → ۴۰۴؛ (ج) بدونِ هدر → شعبه‌ی پیش‌فرض
(رفتارِ فعلی حفظ شود)؛ (د) staffِ قفل‌شده به شعبه → هدر نادیده گرفته شود.

**استراتژیِ برگشت:** تغییر در یک تابع و ایزوله است؛ برگشت = بازگرداندنِ همان بلوکِ
`if`. بدونِ migration، بدونِ تغییرِ داده.

### P0-2 · `POST /api/v1/checkin` بدونِ احراز هویت، وضعیتِ رزرو را جهش می‌دهد

- **فایل‌ها:** `api/src/app/api/v1/checkin/route.ts` · `api/src/lib/tables.ts:73-120`
- **دامنه:** Auth / چرخه‌ی حیاتِ رزرو · **بخشِ ۴ و ۷**
- **شدت: بحرانی.**

**شواهد:** route هیچ فراخوانیِ auth ندارد (نه `authFromRequest`، نه
`withRestaurantAuth`، نه `guardMaintenance`) و هیچ rate-limitِ اختصاصی هم ندارد.
`api/src/middleware.ts` هم — که تنها لایه‌ی سراسری است — فقط سه کار می‌کند:
بنِ IP، چکِ Origin برایِ CSRF، و rate-limitِ سراسری. **احراز هویت نمی‌کند.**
پس این endpoint واقعاً عمومی است.

**اثرِ واقعی:** با تنها یک `qr_code`، مهاجمِ ناشناس می‌تواند رزروِ فردِ دیگری را
`checked_in` سپس `seated` کند (دو انتقالِ واقعیِ چرخه‌ی حیات، با audit، SMS و رویدادِ
اقتصادی)، و میز را `occupied` کند. پاسخ هم `reservation_code` را برمی‌گرداند
(نشتِ اطلاعات و کلیدِ اقداماتِ بعدی). این هم **دستکاریِ حالتِ کسب‌وکار** است و هم
یک **DoSِ عملیاتی**: با اسکنِ QRها می‌شود میزهایِ یک رستوران را اشغال نشان داد.

**ریشه:** طراحی برایِ «مهمان QR رویِ میز را اسکن می‌کند» — یعنی عمداً بدونِ لاگین.
اما مالکیتِ `qrCode` هیچ‌وقت اثباتِ حضور نیست؛ QR رویِ میز عکس‌برداری/حدس‌زدنی است.

**رفعِ پیشنهادی (بدونِ شکستنِ سناریویِ مهمان):** سه لایه، به ترتیبِ اولویت:
1. rate-limitِ اختصاصی و تهاجمی رویِ IP برایِ همین مسیر (هم‌اکنون غایب) — کمترین ریسک، فوری.
2. الزامِ اثباتِ زمینه: check-in فقط در پنجره‌ی زمانیِ رزرو (هم‌اکنون هست: −۳۰ دقیقه تا `slotEnd`) **به‌علاوه‌ی** یک عاملِ دوم — یا JWTِ مشتری (اگر لاگین است، باید `userId` رزرو با آن یکی باشد)، یا `guest_token`ِ رزرو، دقیقاً همان الگویی که waitlist برایِ رفعِ IDOR در migration 041 استفاده کرده (`WL.guest_token`). **این الگو در همین ریپو موجود است — دوباره اختراع نمی‌شود (§۲۲).**
3. عدمِ بازگرداندنِ `reservation_code` به فراخوانِ بدونِ احراز هویت.

**ریسک:** اگر QRهایِ چاپ‌شده‌ی فعلی توکن ندارند، الزامِ توکن جریانِ موجود را می‌شکند.
**وابستگی:** باید اول بررسی شود آیا `Table.qrCode` تنها داده‌ی QR است یا رزرو
`guest_token` دارد. **این یک ناشناخته است و پیش از پیاده‌سازی چک می‌شود** —
اگر توکن در دسترس نبود، لایه‌ی ۱ و ۳ فوراً اعمال و لایه‌ی ۲ با طراحیِ QRِ رزرو-محور
به‌عنوانِ موردِ فازِ ۳ ثبت می‌شود (به‌جایِ شکستنِ محصول).

**استراتژیِ تست:** درخواستِ بدونِ auth با `qr_code`ِ معتبر → باید رد شود؛
درخواستِ خارج از پنجره‌ی زمانی → رد؛ فراخوانیِ مکرر → ۴۲۹؛ مسیرِ مجاز → همچنان `seated`.

**استراتژیِ برگشت:** تغییر محدود به یک route و یک تابع؛ بدونِ migration.

#### 🔁 یادداشتِ صداقت — یک خطایِ من که ناوگانِ بازبینی گرفت

این یافته محصولِ یک **اشتباهِ خودم** بود و ثبتش لازم است:

در Batch 6 یکی از یافته‌هایِ ناوگان (`birth-month-gregorian-shown-as-jalali`)
می‌گفت پنل عددِ ماهِ **میلادی** را در نام‌هایِ ماهِ **شمسی** ایندکس می‌کند. من
پذیرفتم و نمایش را به نام‌هایِ ماهِ میلادی تغییر دادم.

در اجرایِ دومِ ناوگان، یک بازبینِ مستقل همان یافته را **رد کرد** با ردیابیِ
مسیرِ نوشتن: کشوییِ واک‌ین از اول ماهِ **شمسی** می‌فرستد، پس نمایشِ شمسی
**درست بود** و تغییرِ من یک باگ **وارد کرده بود**. تغییر بازگردانده شد.

ولی همان ردیابی نشان داد مشکلِ واقعی جایِ دیگری است: نه در *نمایش*، بلکه در
*مقایسه‌ی cron*. یعنی یافته‌ی اولیه در تشخیصِ محل غلط بود، در حسِ اینکه
«اینجا یک ناهماهنگیِ تقویمی هست» درست.

**درسِ روشِ کار:** بازبینیِ خصمانه فقط جلویِ یافته‌هایِ غلطِ *عامل‌ها* را
نمی‌گیرد — جلویِ اصلاحاتِ غلطِ *من* را هم می‌گیرد. اگر فقط اجرایِ اول را
داشتم، یک رگرسیونِ خاموش کاشته بودم و باگِ واقعی هم باز می‌ماند.

  می‌شوند (۲۷/۲۷). ریشه: جریان‌هایِ چندمرحله‌ای از مهلتِ پیش‌فرضِ ۳۰ثانیه رد
  می‌شوند. **بخشی رفع شد** (`test.slow()` رویِ ۴ specِ متأثر، بدونِ ضعیف‌کردنِ
  هیچ assertion). دو specِ دیگر (`social-proof`, `accessibility`) هنوز زیرِ بارِ
  ۴-ورکر ناپایدارند — با پیکربندیِ واقعیِ CI (۲ ورکر + ۲ retry) به‌احتمالِ زیاد
  سبزند ولی این تأیید نشده. جزئیاتِ کامل در `BASELINE-TEST-STATUS.md` §۳.۲.

---

## ۷. ترتیبِ اجرا (batchها — طبقِ §۳۱)

هر batch یک واحدِ منطقی و مستقل است. **بینِ هر دو batch، گیتِ کاملِ §۳۰ اجرا
می‌شود** (`sync-design-system --check` + `tsc` + `lint` + `npm test` + E2Eِ مرتبط)
و نتیجه در `BASELINE-TEST-STATUS.md` §۳ ثبت می‌شود.

| Batch | محتوا | یافته‌ها | چرا این ترتیب |
|---|---|---|---|
| **۱** | جداسازیِ شعبه + احراز هویتِ check-in | P0-1، P0-2 | بالاترین شدت؛ بک‌اندی و ایزوله |
| **۲** | حذفِ جعلِ موفقیت در کلاینت | P0-3، P0-4 | مستقل از Batch 1؛ فقط فرانت |
| **۳** | قراردادهایِ frontend↔backend | P1-3، P1-4، P1-5 | بعد از تثبیتِ مسیرهایِ واقعی |
| **۴** | هاردنینگِ تله‌متری + مرزهایِ اعتمادِ داده | P1-1 | نیازِ migration؛ مستقل |
| **۵** | تست‌هایِ رگرسیون + پینِ ثوابتِ معماری | P2-2 + پینِ §۳.۱/§۳.۲ | همه‌ی رفع‌هایِ قبلی را قفل می‌کند |
| **۶** | بنیانِ پروفایل/آلرژی/تولد | P1-2 | بزرگ‌ترین؛ بعد از پایدارشدنِ بنیان |
| **۷** | کدِ مرده و مستندات | P2-1، P2-4 + `DECISIONS.md` | کم‌ریسک‌ترین، آخر |
| **۸** | وفاداری (PRِ جدا) | P1-6 | پرریسک؛ طبقِ `CLAUDE.md` جدا |

**قاعده‌ی توقف (§۳۰):** اگر گیتی شکست، همان‌جا توقف، ریشه‌یابی، رفع، تستِ
رگرسیون، اجرایِ دوباره. **انباشتِ تغییراتِ تأییدنشده ممنوع.**

## ۸. استراتژیِ کلیِ برگشت

- **بدونِ migrationِ مخرب.** هر تغییرِ اسکیما فقط additive و idempotent
  (`ADD COLUMN IF NOT EXISTS`)، با شماره‌ی جدید در `prisma/sql/` — طبقِ `CLAUDE.md`
  فایلِ قبلی هرگز ادیت نمی‌شود. یعنی برگشتِ کد بدونِ برگشتِ DB همیشه امن است.
- **تغییراتِ رفتاریِ بک‌اند** (P0-1، P0-2) در توابعِ کوچک و ایزوله‌اند.
- **تغییراتِ فرانت** حالتِ ماندگارِ سرور ندارند.
- طبقِ `CLAUDE.md`، موردِ پرریسک (P1-6 و هر تغییرِ اسکیما) با PR و CIِ سبز می‌رود،
  نه پوشِ مستقیم به `main`.

## ۹. مواردِ تعویق‌شده — با دلیلِ صریح

طبقِ اصلِ صداقتِ `CLAUDE.md`، آنچه انجام **نمی‌شود** به‌اندازه‌ی آنچه انجام می‌شود
باید صریح باشد:

| مورد | بخشِ پروتکل | دلیلِ تعویق |
|---|---|---|
| P2-5 · `npm audit fix` | §۲۴ | جابه‌جاییِ نسخه‌هایِ ترانزیتیو، در حالی که هنوز پوششِ تراکنشیِ E2E نداریم. بعد از Batch 5 امن‌تر است. |
| بنیانِ AI / نسخه‌بندیِ دیتاست / خطِ لوله‌ی آموزش | §۱۷ | §۱۷ صریحاً overbuild را منع کرده. **مرزِ اعتماد (P1-1) ساخته شد** — چون باید در لحظه‌ی درج ثبت شود و بعداً قابلِ بازسازی نیست — ولی هیچ خطِ لوله/دیتاست/مدلی ساخته نشد. سیاست در `docs/architecture/AI-DATA-ELIGIBILITY.md`. |
| قرنطینه‌ی رویدادِ مشکوک + down-weighting | §۱۵ | تا وقتی هیچ مصرف‌کننده‌ای برایِ `platform_events` نیست، جدولِ قرنطینه چیزی می‌شد که کسی نمی‌خواندش. down-weighting هم بخشی از خطِ لوله‌ی آموزش است، نه ingest. |

## ۱۰. گیتِ اتمامِ فازِ ۲ (§۳۴)

فازِ ۲ فقط وقتی «کامل» اعلام می‌شود که همه‌ی این‌ها **با شواهدِ اجراشده** برقرار باشند:

- [x] مسیرهایِ جعلِ موفقیتِ P0 حذف شده (P0-3، P0-4) + تستِ رگرسیون

- [x] canonical بودنِ چرخه‌ی حیات **با تست پین شده** (§۳.۱) — و در Batch 10 یک
      رقابتِ واقعیِ «دو بار انتقال» در همان نویسنده‌ی canonical پیدا و با
      compare-and-set رفع شد (ADR-P2-012)
- [x] مرجعِ availability مکتوب + تستِ رزروِ هم‌زمان (§۳.۲)
- [x] تله‌متری هاردن‌شده با مرزهایِ اعتماد (P1-1) + سیاستِ نگه‌داری (ADR-P2-014)
