## ۱. محیطِ اجرا (قابلِ بازتولید)

تست‌هایِ بک‌اند به Postgres/Redisِ واقعی نیاز دارند (طبقِ یافته‌ی
`docs/audit/BASELINE.md` §۶: بدونِ DBِ متصل، `tests/_all.runner.mts` کلِ ۴۳۴ تست را
به‌صورتِ آبشاری کنسل می‌کند، نه فقط تست‌هایِ integration را).

```bash

       -e POSTGRES_DB=rezervno_test -p 55432:5432 postgres:16

export DATABASE_URL="postgresql://test:test@localhost:55432/rezervno_test"
export REDIS_URL="redis://localhost:56379"
export JWT_ACCESS_SECRET="testsecret_access_0123456789abcdef"
export JWT_REFRESH_SECRET="testsecret_refresh_0123456789abcdef"

cd api
npx prisma generate
npx prisma db push --skip-generate --accept-data-loss   # ← لازم است، پایین را بخوان
sh prisma/apply-sql.sh
npm test
```

### ⚠️ یافته‌ی جدیدِ زیرساختی (این نشست، در هیچ سندِ قبلی نبود)

`prisma/apply-sql.sh` رویِ یک دیتابیسِ **کاملاً خالی** شکست می‌خورد:

```
→  001-performance-indexes.sql
Error: P1014  The underlying table for model `reservations` does not exist.
✗ اعمالِ 001-performance-indexes.sql ناموفق — متوقف شد
```

دلیل: `prisma/sql/001-*` یک migrationِ **افزایشی** (ایندکس رویِ جدولِ موجود) است،
نه سازنده‌ی اسکیما. یعنی برخلافِ آنچه `CLAUDE.md` می‌گوید
(«اجرایِ همه‌ی migrationها رویِ یک DBِ خالی: `prisma/apply-sql.sh`»)، این اسکریپت
به‌تنهایی **نمی‌تواند** یک DB خالی را بالا بیاورد؛ اول باید اسکیمایِ پایه ساخته شود
(`prisma db push` یا یک دامپ). این یک **شکافِ مستندسازی/راه‌اندازی** است که هر
توسعه‌دهنده‌ی تازه‌وارد به آن می‌خورد.

**وضعیت:** ثبت‌شده به‌عنوانِ P2-4 در `PHASE-2-PLAN.md` (رفعِ مستندات + راهنمایِ
پیامِ خطا). رفع نشد چون تغییرِ رفتارِ migration runner بدونِ نیاز، ریسکِ اضافه است.

### ⚠️ یافته‌ی جدیدِ E2E: ناپایداریِ وابسته به بار (نه رگرسیون)

اجرایِ کاملِ سوئیتِ Playwright به‌صورتِ محلی با **۴ ورکر و بدونِ retry** انجام شد
(پیکربندیِ CI محافظه‌کارتر است: `workers: 2` و `retries: 2`).

**اجرایِ اول:** ۱۳۰ پاس / ۵ شکست. هر ۵ شکست دقیقاً در یک نقطه بودند — دکمه‌ی
«ادامه» در شیتِ رزرو — در `booking.spec`، `booking-context.spec` و `waitlist.spec`.

**تشخیص (نه فرض):** همان ۵ تست با `--workers=1` اجرا شدند → **۲۷/۲۷ پاس**،
از جمله `booking.spec.ts:24` («جریانِ کاملِ رزرو تا تأییدیه با کدِ رزرو») که
دقیقاً از مسیرِ تغییریافته‌ی `confirmBook` عبور می‌کند. یعنی این‌ها **رگرسیونِ
تغییراتِ فازِ ۲ نیستند**، بلکه ناپایداریِ زمانیِ از‌پیش‌موجود زیرِ بارِ موازی‌اند:
این جریان‌ها چندمرحله‌ای‌اند و از مهلتِ پیش‌فرضِ ۳۰ ثانیه‌ی Playwright رد می‌شوند.

**رفع:** `test.slow()` به سه specِ متأثر اضافه شد (همان کاری که برایِ specِ جدید
هم انجام شد). **هیچ assertionی ضعیف یا حذف نشد** — فقط مهلت بیشتر شد، چون
مسئله سرعتِ محیط بود نه درستیِ ادعا.

**اجرایِ دوم (بعد از رفع):** ۱۳۳ پاس / **۲ شکست** — و این دو **تستِ متفاوتی‌اند**
(`social-proof.spec.ts:66`, `accessibility.spec.ts:14`) در فایل‌هایی که اصلاً
لمس نشده‌اند. آن‌ها هم با `--workers=1` اجرا شدند → **۲۷/۲۷ پاس**.

**نتیجه‌گیریِ صادقانه:** سوئیتِ E2E یک ناپایداریِ ساختاریِ وابسته به بار دارد که
مستقل از کارِ فازِ ۲ است و **در هیچ سندِ قبلی ثبت نشده بود**. با پیکربندیِ واقعیِ
CI (۲ ورکر + ۲ retry) به‌احتمالِ زیاد سبز می‌شود، ولی «به‌احتمالِ زیاد» ادعایِ
سبزبودن نیست. ثبت‌شده به‌عنوانِ **P2-6** در `PHASE-2-PLAN.md`.
**ادعا نمی‌کنم کلِ سوئیتِ E2E سبز است.**

### دو یافته‌ی روشِ کار در همین batch

**۱. تستِ من یک نقصِ ساختاری در رفعِ خودم را گرفت.** آزادسازیِ میز را ابتدا
داخلِ شرطِ `if (result.changed && notify)` گذاشتم. تست با `notify:false` صدا زد و
شکست خورد — و معلوم شد **باطل‌سازیِ کشِ availability هم از قبل** در همان بلوک
گیر افتاده بود، یعنی هر فراخوانیِ `notify:false` بی‌صدا کش را باطل نمی‌کرد.
اعلان و یکپارچگیِ داده به یک پرچمِ مشترک گره خورده بودند؛ حالا جدا شده‌اند.

**۲. یک تستِ من فرضِ غیرممکن داشت و بازنویسی شد.** تستِ «اگر رزروِ فعالِ دیگری
میز را اشغال کرده…» برایِ ساختنِ شرایط به دو رزروِ فعالِ هم‌پوشان روی یک میز
نیاز داشت — و **دیتابیس درجش را رد کرد** (کانسترینتِ `EXCLUDE USING gist`).
یعنی سناریو از اساس دست‌نیافتنی است. به‌جایِ ادعایِ چیزی که هرگز رخ نمی‌دهد،
تست بازنویسی شد تا همان چیزی را بسنجد که واقعاً تضمین شده — و این دقیقاً
ادعایِ ADR-P2-002 است (مرجعِ تداخل = دیتابیس). گاردِ کد به‌عنوانِ
defense-in-depth باقی ماند.
